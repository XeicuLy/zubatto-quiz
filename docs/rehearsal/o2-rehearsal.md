# O2 のリハーサルの記録

本番の前に、本番の環境で5部屋 × 50接続の負荷をかけ、次の3つを確かめた記録。

- P1（1秒以内に全員へ届く）・P3（回答を取りこぼさない）・P4（締切から2秒以内に結果を出せる）を満たすか（O2・SC2・ADR 0001）
- Workers・Durable Objects・D1 の使用量が、1回の本番でどれくらいになるか（C1・C4・ADR 0005）
- デプロイで接続が切れても、自動でつなぎ直してゲームを続けられるか（A1）

満たさなかった項目は、[下の「満たさなかった項目と対策」](#満たさなかった項目と対策)に対策の Issue を書く。

## 使用量

負荷の直前と直後に、[stop-and-usage.md](../runbooks/stop-and-usage.md#本番の前後に確かめる)の手順でダッシュボードの数を控え、差を取った。

### 見積もり（負荷の前に立てたもの）

1回のリハーサル（5部屋 × 50体 × 3問）で、どれくらい使うかの見積もり。少なく見積もらないよう、DO が受け取る WebSocket のメッセージは1通を1リクエストと数える。料金の計算では20通を1リクエストとするが、メトリクスは実際の通数で出て、無料プランの1日の上限がどちらで数えるかは書かれていない（2026-10-20 に Cloudflare の料金のページで確かめた）。

| 何の                         | 数え方                                                                                                        | 見積もり     | 1日の上限          |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------- | ------------ | ------------------ |
| Workers のリクエスト         | WebSocket の接続 255 本 + HTTP（問題セットを作る・部屋を5つ作る・消す）7 本。API の Worker の分も同じ数とする | 約 530       | 100,000            |
| Durable Objects のリクエスト | 接続 255 + join 250 + 回答 750 + ホストの進行 約 75 + 部屋の初期化 5 + alarm 数十                             | 約 1,400     | 100,000            |
| DO の SQLite に書いた行      | 参加者 250 + 回答 750 + 得点 750 + 部屋と問題の行。索引への書き込みも行に数えるので、その倍ほど               | 3,000〜5,000 | 100,000            |
| DO の SQLite で読んだ行      | join のたびの名前の照合（部屋ごとに 50 × 50 ÷ 2）と、締切ごとの集計                                           | 1万〜3万     | 5,000,000          |
| D1 で読んだ行・書いた行      | ログインのセッションの確認と、問題セットの作成・削除だけ                                                      | 数十〜数百   | 5,000,000・100,000 |

### 測った数

前は 20:14、後は 20:30 ごろ（負荷が終わってから約10分あと。ダッシュボードの反映は遅れるため）に控えた。どれも 0:00 UTC（日本時間 9:00）からのアカウント全体の数で、前の数はすべて 0 だったので、差は後の数と同じ。差には、試した1部屋 × 20体の回と、ホストのログイン・ログアウトも入っている。

| 何の                         | 前  | 後（＝差）       | 1日の上限   | 上限に対する割合 |
| ---------------------------- | --- | ---------------- | ----------- | ---------------- |
| Workers のリクエスト         | 0   | 590              | 100,000     | 0.6%             |
| Workers Logs のイベント      | 0   | 2,052            | 200,000     | 1.0%             |
| Durable Objects のリクエスト | 0   | 約 2,000         | 100,000     | 2%               |
| Durable Objects の実行時間   | 0   | 1.25 GB-s        | 13,000 GB-s | 0.01%            |
| DO の SQLite で読んだ行      | 0   | 約 91,000        | 5,000,000   | 1.8%             |
| DO の SQLite に書いた行      | 0   | 約 3,000         | 100,000     | 3%               |
| D1 で読んだ行                | 0   | 148（93 クエリ） | 5,000,000   | 0.003%           |
| D1 に書いた行                | 0   | 24               | 100,000     | 0.02%            |

- DO のリクエストとストレージの行は、ダッシュボードが「2k」「91k」のように丸めて出すので、約で書いた。エラーはどれも0件
- DO のリクエストが見積もりより多いのは、接続が閉じたときの呼び出し（`webSocketClose`、約270本）を数えていなかったため。足すと 1,800 ほどになり、測った数に近い
- DO の SQLite で読んだ行は、見積もりの3倍ほどだった。回答のたびに、ホストへ送る回答の数（`answerProgress`）のために回答と参加者を数え直していて、1部屋 × 1問で 50 × 50 行ほどになる。上限には遠いので、このままでよい
- `wrangler d1 info zubakui` の24時間の数（20:22 に読んだ行 74・書いた行 37）は、ダッシュボードと少しずれた。集計の時刻が違うためで、ダッシュボードの数を使う

### 1回の本番あたりの目安

本番は1部屋 × 20名前後 × 10問（要件の「20名・10問の例」）。測った数を、もとになる操作の数で割り戻して見積もった。つなぎ直し（リロードやスリープからの復帰）は、1人3回ほどとして、接続を約80本とした。

| 何の                         | 何に比例するか                                        | リハーサル         | 1回の本番の目安 | 1日の上限に対する割合 |
| ---------------------------- | ----------------------------------------------------- | ------------------ | --------------- | --------------------- |
| Workers のリクエスト         | 接続の数（画面と API の Worker で1本につき2回）       | 590（接続 276 本） | 約 200          | 0.2%                  |
| Workers Logs のイベント      | Worker と DO の呼び出しの数（1回につき約0.8件）       | 2,052              | 約 600          | 0.3%                  |
| Durable Objects のリクエスト | 接続・join・resume・回答・進行・接続が閉じた数        | 約 2,000           | 約 500          | 0.5%                  |
| DO の SQLite で読んだ行      | 部屋ごとに 問題数 × 人数² と、join・resume ごとの人数 | 約 91,000          | 約 1万          | 0.2%                  |
| DO の SQLite に書いた行      | join・回答・得点の数（索引の分を足して約1.6倍）       | 約 3,000           | 約 700          | 0.7%                  |
| D1 で読んだ行・書いた行      | ログインと、部屋を作るときに問題セットを読む分        | 148・24            | 数百・数十      | 0.1% 未満             |

- 1回の本番は、どの上限に対しても1%に届かない。いちばん近いのは DO の SQLite に書いた行で、それでも100回ほど余裕がある
- 5部屋 × 50名（SC1・SC2 の上限）で遊んでも、今回のリハーサルとほぼ同じで、どれも3%ほどに収まる
- リハーサルと本番を同じ日に行っても、上限には届かない。それでも本番の前には、その日の数を確かめ、ほかで使っていないかを見る（[stop-and-usage.md](../runbooks/stop-and-usage.md#本番の前後に確かめる)）

## デプロイで切れたときに戻れるか（A1）

負荷とは別に、小さく1ゲームを行って試した。ボットはつなぎ直しをしないので、負荷の途中でデプロイすると、その回の表が壊れるため。

結果: **満たした**。デプロイの途中でもゲームは止まらず、得点を失わずに最終ランキングまで進んだ。ただし、思っていたのと違い、デプロイでは接続が切れなかった。そこで、自動のつなぎ直しは、接続をわざと切って別に確かめた。

### 行ったこと

2026-10-20 20:40〜20:49（日本時間）。ホストは PC のブラウザ、回答者は Playwright で開いたスマホの幅（390 × 844）のブラウザ2つ（プレイヤー1・2。コンテキストを分け、秘密も別）。問題は2問で、どちらも制限時間60秒。

- tail では、この間の例外は0件だった

### わかったこと

- **眠っている部屋の DO は、API の Worker をデプロイしても WebSocket が切れなかった**。Cloudflare のドキュメントには「コードの更新を含むデプロイは、すべての DO を再起動し、WebSocket を切る」と書かれている（2026-10-20 に Durable Objects の WebSockets のページで確かめた）。今回は、デプロイの前後 1 分ほど部屋に何も届いておらず、DO は Hibernation で眠っていた。WebSocket は Cloudflare の側が持ったまま、新しい版の DO が受け継いだ。今回の API のコードは前のデプロイと同じ中身だったことも、関係しているかもしれない
- 起きている DO（回答が次々に届いているとき）や、コードの中身が変わるデプロイで切れないかは、確かめていない。そのため、本番中に API の Worker をデプロイしない決まり（ADR 0006・[deploy.md](../runbooks/deploy.md#何が動くか)）は、そのまま守る。切れたときに戻れることは、上のとおり確かめた
- **画面の Worker をデプロイしても、開いている画面は古いコードのまま動く**。プレイヤー1の画面はデプロイの前に開いたままだったので、部屋を終えたあとに #101 より前の文言（「最終の結果はスクリーンで発表されています」）が出た。リロードしたプレイヤー2の画面には、新しい文言と最終ランキングが出た。メッセージの仕様が同じなので、古いコードのままでも遊べる
