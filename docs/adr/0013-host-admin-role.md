# ホストの管理者は許可リストの印で決め、管理者だけが GitHub の名前でホストを足し、外せるようにする

## Status

accepted

## Context

ADR 0003 で、ホストは GitHub ログインと許可リスト（`host_allowlist`）で見分けると決めた。許可リストの追加と削除は開発者が `wrangler d1 execute` で行い、管理画面は作らないことにした（ADR 0003 の DD2、要件定義書のスコープ外）。この形には、次の困りごとがある。

- ホストを足せるのは、D1 にコマンドを打てる開発者だけ。足すたびに、GitHub の数値の ID を `gh api` で調べて SQL に入れている
- 外すときは、runbook の2手順（許可リストから外す → その人のセッションを消す）を、この順に手で行う。`requireHost` は許可リストを確かめ直さないので、手順2を忘れると、外した人のセッションが最大7日残る。その間、問題セットの編集や部屋の作成を続けられる

画面から足せるようにすると、「誰がホストを増やせるか」という認可の境界が変わる。そのため、コード（#291・#292・#293）より先にここで決める。想定は今と同じく、知り合いのホスト1〜5名で、使うのは年に数回。管理者は開発者本人で、増えても1〜2名。

次のことを 2026-11-14 に確かめた（GitHub と D1 は公式の文書を context7 経由で、Better Auth は 1.7.15 の文書で）。

- GitHub の `GET /users/{username}` は、未認証でも呼べる。上限は送り元の IP ごとに 60回/時（`curl -sI` の `x-ratelimit-limit: 60` でも確かめた）。PAT などで認証すると 5,000回/時になる。Workers の出口の IP は、ほかの Cloudflare の利用者と共有している。そのため、こちらが1回も使っていなくても、60回が尽きていることがある。応答の `type` は `User` か `Organization` で、許可リストと照らすのは数値の `id`
- Better Auth の admin plugin は、`user` に `role`・`banned`・`banReason`・`banExpires` を、`session` に `impersonatedBy` を足す。さらに、`/api/auth/admin/*` の入口（ユーザーを作る、役割を変える、なりすますなど）が増える
- D1 の `batch()` の文は、1つの SQL のトランザクションで動く。どれかが失敗すると全部が戻る
- 今の Better Auth の設定は `cookieCache` を使っていない。そのため、`getSession` は要求のたびに D1 を読む

## Decision Drivers

- DD1 セキュリティ（S1）: 管理者でない人（一般のホストも）は、ホストの一覧・追加・外すをできない。管理者の権限を取り消したら、次の要求から効く。画面から管理者を増やせない（権限を上げるのはコマンドだけ）。外したホストのセッションは残らない
- DD2 運用の手間: 管理者は D1 のコマンドを打たず、GitHub の名前を入れるだけで足せる・外せる。コマンドが要るのは、最初の管理者を入れるときと、管理者の付け外しだけ
- DD3 コスト（C1）: 無料で動く。秘密を増やさないほうがよい。年に数回・数人の追加で、GitHub の上限に当たらない
- DD4 変更容易性・テスト（M1）: vitest-plugin の中で、外へ出ずにテストできる。`/api/admin/*` にルートを足して守りを付け忘れたら、テストが落ちる
- DD5 ロックイン耐性（ADR 0008）: Go 版でも、同じ表と同じ判定で作れる。Better Auth への依存を増やさない
- DD6 パフォーマンス（P1）: 進行操作（WebSocket）に、D1 への問い合わせを足さない。HTTP の要求に D1 のクエリが1つ増えるのは許す

## Considered Options

- 軸K: 管理者の印をどこに持つか
  - K1. `host_allowlist` に `is_admin` 列を足す（additive、既定は false）
  - K2. 別のテーブル（`github_user_id` を許可リストへの外部キーにする）
  - K3. Better Auth の admin plugin（`user.role` に `admin` を入れる）
- 軸Q: 管理者かをどう確かめるか
  - Q1. `requireAdmin` が、要求のたびに D1 を読む（キャッシュしない）
  - Q2. 管理者かをセッションに持たせる（セッションの追加の欄や Cookie のキャッシュ）
- 軸N: 管理者でない人への応答
  - N1. 403 `forbidden`
  - N2. 404 `not_found`（S1 の「他人のものはないのと同じ」にそろえる）
- 軸E: 画面からできること
  - E1. 一覧・追加・外すだけ。管理者の行は外せない。管理者の付け外しはコマンド
  - E2. 管理者の付け外しも画面からできる
- 軸V: 外したあとのセッション
  - V1. 外す API が、許可リストの行とその人のセッションを `db.batch` で一緒に消す。`requireHost` は今のまま確かめ直さない
  - V2. V1 に加えて、`requireHost` でも要求のたびに許可リストを確かめ直す
- 軸G: GitHub の名前から ID をどう引くか
  - G1. 未認証の `GET /users/{username}`
  - G2. トークン（公開の情報を読むだけの PAT）を `wrangler secret` で入れて呼ぶ
  - G3. 名前から引かない。管理者が数値の ID を入れる

## Decision Outcome

採用する選択肢: 「K1・Q1・N1・E1・V2・G1」。管理者の印は許可リストの列に持ち、`requireAdmin` が要求のたびに D1 を読んで確かめ、管理者でなければ 403 を返す。画面からは一覧・追加・外すだけができ、外すときはセッションも一緒に消す。そのうえで `requireHost` も許可リストを確かめ直す。名前から ID を引くのは、未認証の GitHub API で始める。

軸ごとの比べ合いは次のとおり。

決めた形は次のとおり。

- 管理者の印: `host_allowlist.is_admin`（`integer` の boolean、`NOT NULL DEFAULT false`）。migration は `db:generate` で作り、今ある行は管理者でない。最初の管理者は、runbook のコマンドで `is_admin` を true にする
- `requireAdmin`: `csrf()`・`requireHost` のあとに置き、要求のたびに「その user の GitHub の account が、`is_admin` が true の許可リストの行にあるか」を D1 で確かめる。管理者でなければ 403 `{ "error": "forbidden" }`
- `requireHost`: セッションを確かめたあと、許可リストにあるかも確かめ直す（今の `isAllowedUser` と同じ判定）。なければ、セッションがないときと同じ 401 `unauthorized`
- `GET /api/me`: `requireHost` だけを通り、`{ isAdmin }` を返す。画面が管理者向けのリンクを出すために使う。守りの本体は `requireAdmin` で、画面の制限は見た目だけ
- `/api/admin/hosts`: `.use(csrf(), requireHost, requireAdmin)` の下に、一覧（GET）・追加（POST、本文は `{ login }`）・外す（`DELETE /api/admin/hosts/{githubUserId}`）を置く
- 追加
  - 名前は protocol の zod で形（英数字とハイフン、1〜39文字）を確かめ、合わなければ GitHub に送らずに 400
  - 送り先は `https://api.github.com/users/` に固定し、名前は `encodeURIComponent` で入れる。`User-Agent` を付け、`AbortSignal.timeout` で待つ時間を区切る。応答は zod で読む
  - 結果: 見つかって `type` が `User` なら、数値の `id` を文字列にして許可リストに入れる。名前は変えられるので、足したときの名前を `note` にメモとして入れるだけにする。見つからない・`type` が `User` でない → 404 `not_found`。すでにある → 409 `already_exists`（`onConflictDoNothing` で、同時に2つ来ても1行だけ）。GitHub の 403・429・5xx、時間切れ、応答の形の違い → 502 `github_unavailable`
- 外す
  - 管理者の行は外せない（自分も、ほかの管理者も）。409 `admin_host`
  - その人のセッションの削除と許可リストの行の削除を、`db.batch` で1回に行う。どちらの DELETE にも `is_admin = false` の条件を入れ、判定と削除の間に管理者になっても消さない
  - 許可リストにない ID → 404 `not_found`
- ログ: GitHub の名前も ID も出さない（ログは決まったキーだけ）

## Consequences

- 良い影響: 管理者は、D1 のコマンドを打たずに、GitHub の名前だけでホストを足し、外せる。外すときのセッションの消し忘れがなくなる
- 良い影響: `requireHost` が許可リストを確かめ直すので、コマンドで許可リストだけを外しても、次の HTTP の要求から 401 になる。runbook の手順2（セッションを消す）は、行の掃除になる
- 良い影響: 権限を上げられるのは、今と同じく `wrangler` にログインできる人だけ。管理者のアカウントを乗っ取られても、作られるのは一般のホストまで
- 悪い影響: Worker が外（`api.github.com`）へ `fetch` する初めての経路になる。送り先を固定し、名前の形を先に確かめ、待つ時間を区切る
- 悪い影響: Workers の共有の出口 IP で、未認証の上限（60回/時）に当たると、追加が 502 になる。そのときは時間をおいて入れ直す
- 悪い影響: ホストの HTTP の要求ごとに、D1 のクエリが1つ増える（D1 の無料枠の読み取りに比べて、十分に小さい）
- 悪い影響: 管理者でないホストへの 403（`forbidden` の JSON）と、`csrf()` の 403（テキスト）が、同じ状態で並ぶ。openapi.json の 403 には両方の形を書く（400 の `BadRequest` と同じ書き方。[ADR 0014](0014-keep-api-contract-with-admin-routes.md)）
- 悪い影響: 管理者の付け外しと、管理者のホストを外すことは、コマンドでしかできない
- 悪い影響: つながったままのホスト用の WebSocket は、外しても閉じるまで進行操作を続けられる（P1・ADR 0003 のまま）。すぐに止める方法は runbook の「すぐに止めたいとき」のまま
- 対応事項（#291）: `is_admin` の列と migration を足し、`isAdminUser` と `requireAdmin`（403 `forbidden`）、`GET /api/me` を作る。`httpErrorSchema` に `forbidden` を足す。テストの道具（`resetHosts`・`allowGithubUser`）で管理者を作れるようにし、E2E 用の管理者のログインは `test/e2e-entry.ts` にだけ足す。runbook に、最初の管理者を入れるコマンドと、管理者の付け外しのコマンドを書く。管理者のホストを外すときは、先に印を外してから外す
- 対応事項（#292）: `requireHost` で許可リストを確かめ直す（ホスト用の WebSocket の入口も、つなぐときに確かめ直すことになる）。`lookupGithubUser` と `/api/admin/hosts` を作り、`httpErrorSchema` に `already_exists`・`admin_host`・`github_unavailable` を足す。runbook の「外す」を、画面からの操作とコマンドの両方で書き直す
- 対応事項（#293）: `/admin/hosts` の画面を作る。管理者にだけリンクを出し、管理者の行には外すボタンを出さない。画面の制限は見た目だけで、守りは `requireAdmin` にある
- 対応事項（#291・#292）: 次のセキュリティと同時実行のケースを、自動テストで確かめる
  - `/api/admin/*` のすべての経路で、匿名は 401、一般のホストは 403、管理者は通る。経路は `app.routes` から拾い、ルートを足して守りを付け忘れたら落ちるようにする
  - 管理者の印をコマンドで外すと、次の要求から 403 になる
  - 画面から外した人のセッションも、コマンドで許可リストだけを外した人のセッションも、次の HTTP の要求で 401 になる
  - 管理者の行は、DELETE で外せない（409）。その人のセッションも残る
  - 同じ人を同時に2回足しても、許可リストは1行で、片方は 409
  - 名前の形が違えば GitHub に送らない。送り先は `api.github.com` だけで、名前は `encodeURIComponent` で入る。`type` が `Organization` なら 404。GitHub の 403・429・5xx・時間切れは 502
- 対応事項: 本番で 502 `github_unavailable` が続き、時間をおいても通らなかったら、G2（PAT を `wrangler secret` で入れる）へ移る。そのときは `secrets.required`・`.dev.vars.example`・runbook を同じ変更で直し、この ADR に追記する
- 対応事項: 要件定義書の S1 に管理者の決まりを足し、スコープ外の「ホストを管理する画面」の行を外す。ADR 0003 の許可リストの対応事項に、この ADR を指す一言を足す（ADR 0003 の決定は変えない）。docs/README.md の一覧と、CLAUDE.md の ADR の範囲を直す
