# 問題セットは Cloudflare D1 に持ち主ごとに保存し、部屋を作るときに部屋の DO へコピーする

## Status

accepted

## Context

F4・F7 では、ホストが本番の前に問題セットを作って保存し、本番で部屋に結びつける。ADR 0001 で、進行中のゲームの状態（参加者・回答・締切済みの得点 = A3）は部屋ごとの Durable Object（DO）の SQLite に置くと決めた。しかし、部屋をまたいで残る問題セットの保存先と、それを部屋の DO に渡す方法は決まっていない。想定するのは、ホスト1〜2名（1年後に5名程度）、1セット10問・4択が中心、1問約0.5KB、全体で0.5MB 程度、保存は1日100回以下という量である。本番中に部屋の問題が途中で変わってはならず、同じセットを同時に複数の部屋で開くことはない。ホストの見分け方は次の ADR で決めるため、ここでは「持ち主ごとに分けて保存できること」だけを条件にする。F6（画像つき問題）の画像の置き場所と、過去の結果・ランキングの保存（nice to have）は、見通しだけを書く。各サービスの仕様・無料枠は、2026-10-10 時点の公式ドキュメント（context7 経由を含む）で確かめた。

## Decision Drivers

- DD1 運用・ランニングコスト（C1〜C4）: 想定の量で無料枠に収まる / 上限を超えても課金されずエラーで止まる、またはカード登録が要らない / 使用量を確認できる / 数ヶ月使わなくてもデータが消えず、手作業なしで使い続けられる
- DD2 セキュリティ（S1・S2）: 持ち主の ID ごとに分けて保存し、サーバー側で持ち主の分だけ読み書きできるように絞れる / 保存先の接続情報や API を回答者の端末に渡さず、正解を含むデータはサーバーからしか読めない
- DD3 ロックイン耐性（ADR 0001 の D5）: Go + Cloud Run へ置き換えるとき、公式の手段でデータを標準的な形式（SQL か JSON）で取り出せる。または同じ DB を Go から使い続けられる
- DD4 変更容易性・テスト（M1・M2）: ローカルの Workers ランタイム（vitest-pool-workers / wrangler dev）で、外部のアカウントや通信なしにテストでき、CI でも通る
- DD5 パフォーマンス・可用性（P1・P4・A1）: 出題や締切のたびに保存先へ読みに行かず、本番中の進行が部屋の DO だけで完結する
- DD6 学習コスト・期限: ADR 0001 の40〜80時間に収まる。Cloudflare 以外のアカウントや SDK を増やすほど不利とする

## Considered Options

- 問題セットの保存先
  1. Cloudflare D1
  2. ホストごとの DO の SQLite（2a）/ 全体で1つの DO の SQLite（2b）
  3. Workers KV
  4. 外部の無料 DB: Turso（4a）/ Neon（4b）/ Supabase（4c）
  5. R2 に JSON ファイル
  6. ホストの端末に保存し、JSON で書き出し・読み込み
- 部屋の DO への受け渡し方
  - a. 部屋を作るときにコピーする
  - b. 出題のたびに読みに行く

## Decision Outcome

採用する選択肢: 「Cloudflare D1 に持ち主ごとに保存し、部屋を作るときに部屋の DO へコピーする（1 + a）」。

理由:

- DD1・DD2・DD5 は、残った候補（Cloudflare D1、2a、2b、Neon）がどれも同じくらい満たしており、差がついたのは DD3・DD4・DD6 だった。Cloudflare D1 は DD4・DD6 で最も良い
  - Workers Free で使え（1日に読み500万行・書き10万行、1DB 500MB）、想定の量は枠の1%未満。上限を超えると「クエリがエラーになる」と公式に明記されており、課金されない。放置しても消えない
  - `owner_id` の列と WHERE で持ち主ごとに絞れる。binding で接続するので、回答者の端末から接続する経路がない
  - ローカルの Workers ランタイムで本物どおりに動き、マイグレーションも wrangler で管理できるため、implement-issue の TDD に乗せやすい。Cloudflare の中だけで済み、普通の SQL で書ける
  - DD3 は Neon に劣るが、`wrangler d1 export` で SQL として書き出せる。データが0.5MB しかないので、置き換えのときは書き出して変換するスクリプトで十分補える
- 2a（ホストごとの DO）は S1 を仕組みで保証できるが、書き出し機能がなく、本番環境では DO の一覧を取れない。そのため、Go へ移すときにホストの名簿を別に持って1つずつ書き出す処理を自作する必要があり、DD3 で D1 に劣る
- 2b（全体で1つの DO）は、マイグレーション・書き出し・ダッシュボードといった D1 が提供している機能を自作するのに近く、DD6 で D1 に劣る
- 4b（Neon）は、Postgres なので Cloud Run からもそのまま使え、DD3 では最も良い。しかし、ローカルとテストには Postgres のコンテナかモックが必要で vitest-pool-workers の中で完結せず、アカウントとドライバ（または Hyperdrive）も増えるため、DD4・DD6 で劣る
- 3（KV）は、変更が見えるまで60秒以上かかることがある（結果整合性）。保存の直後に部屋を作ると古い版がコピーされる危険があるため除外した
- 4a（Turso）は10日使わないとアーカイブされ、4c（Supabase）は7日使わないと一時停止する。どちらも手作業で戻す必要があり、年に数回しか使わない使い方では DD1 を満たさないため除外した
- 5（R2）は、超えた分が請求され、有効にするにはサブスクリプションの手続きが必要になる。問題セットのためだけに導入する理由がないため除外した
- 6（ホストの端末）は、PC で作ってスマホで進行するときに JSON ファイルを手で移す必要がある。さらに Safari は7日使わないサイトの保存データを消すため、DD1 を満たさず除外した
- 受け渡し方は a（コピー）を選んだ。本番中は保存先に一度も読みに行かないため、D1 の遅延や障害が P1・A1 に影響しない。コピーした時点で部屋の中身が固まるので、本番中に問題が変わらないことを、編集を禁止するロックで作り込む必要もない。b は保存先の遅延が P1 の経路に入り、保存先の障害がそのまま進行の停止になるうえ、同じ版を出し続けるためのロックも必要になるため、すべての項目で a と同等以下だった

## Consequences

- 良い影響: 本番中の進行が部屋の DO だけで完結し、D1 の遅延や障害が進行に影響しない
- 良い影響: コピーした版が部屋の正本になるので、使用中の編集を禁止するロックが要らない。元の問題セットを編集しても、開いている部屋には影響しない
- 良い影響: Cloudflare 以外のアカウントが増えず、問題セットの保存から部屋の作成までを、D1 を含めてローカルの Workers ランタイムでテストできる
- 悪い影響: S1 は仕組みではなく、クエリごとに `owner_id` で絞ることで守る。絞り忘れがそのまま他人の問題セットの漏えいになる
- 悪い影響: 問題セットが D1 と部屋の DO の2か所にある。部屋を作ったあとに元を直しても、その部屋には反映されない（直したいときは部屋を作り直す）
- 悪い影響: D1 の SQL は SQLite の方言なので、Go へ置き換えるときに Postgres（Cloud SQL など）を選ぶと、スキーマとデータの変換が必要になる
- 対応事項: D1 で問題セットを読み書きする層では `owner_id` を必須の引数にし、他人の問題セットを読めない・書けないことを自動テストで確かめる。`owner_id` に何を入れるかは、ホストの見分け方の ADR で決める
- 対応事項: 部屋を作るときは、問題セット全体（正解を含む）を D1 から1回で読み、部屋の DO の SQLite に1トランザクションで書き込む。正解は部屋の DO の外へ、締切の処理まで出さない（S2）
- 対応事項: 部屋の画面に、「部屋を作ったあとの問題セットの編集は、この部屋には反映されない」ことを表示する
- 対応事項: C4 として、D1 の使用量をダッシュボードの Row Metrics で確認できるようにし、停止手順を ADR 0001 の対応事項と合わせて README に書く
- 対応事項: Go + Cloud Run への置き換えの ADR で、`wrangler d1 export` から新しい保存先へ移す手順を検討する
- 見通し（F6 の画像）: まずは D1 に BLOB で入れる（1枚200KB 程度で、1行の上限2MB に収まる。1,000枚でも1DB 500MB に入る）。部屋を作るときに画像も部屋の DO へコピーし（1部屋あたり約2MB）、部屋の DO から配信することで、本番中に D1 へ読みに行かない原則を保つ。量が増えたら R2 を別の ADR で検討する。R2 は超えた分が請求されるので、使う前に C4 の通知と停止手順を整える
- 見通し（過去の結果・ランキング）: 部屋が終わったときに、部屋の DO から D1 へ結果を書き出す形で後から足せる。必要になったら要件に足してから決める
