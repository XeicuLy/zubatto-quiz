# バックエンドは TypeScript（Hono）+ Cloudflare Workers + Durable Objects で WebSocket を使い、忘年会後に Go + Cloud Run へ置き換える

## Status

accepted

## Context

ズバクイでは、ホストの進行操作（出題 → 受付開始 → 締切）を、最大5部屋 × 50名の回答者へ1秒以内に届ける必要がある。そのための通信方式と、それを動かすバックエンドの言語・デプロイ先が決まっていない。期限は2026年12月の忘年会（約2ヶ月）で、バックエンドとインフラに使えるのは週5〜10時間（合計およそ40〜80時間）。Go は AI と一緒なら HTTP API を書けるが、自力では文法を学習中である。フロントエンド（TanStack Start の SPA を Cloudflare Workers に置く）、DB の選定、ホストの見分け方は対象外とする。各サービスの仕様・無料枠は 2026-10-10 時点の公式ドキュメント（context7 経由を含む）で確かめた。

## Decision Drivers

- D1 パフォーマンス・可用性（必須）: P1 ホストの操作がサーバーに届いてから全回答者の画面が変わるまで1秒以内 / A2 入室時のコールドスタートは許容し、入室後のホストの最初の進行操作から P1 を満たす / P3 50名が締切直前に一斉回答しても取りこぼさない / SC2 5部屋を同時に開いても満たす / A3 締切済みの得点をプロセスの外に永続化できる / A1 1〜2時間の本番中に切れない、または自動で再接続して続けられる
- D2 運用・ランニングコスト: C1 想定の利用量（5部屋 × 50名 × 2時間）で無料枠に収まる。超えても、すぐ止められて月500円以内 / C2 D1 を満たせないなら D1 を優先 / C3 常時起動のインスタンスがない / C4 予算アラートと停止手順を用意できる
- D3 学習コスト・期限: 40〜80時間で、本番実装と O2 のリハーサルまで間に合う。要件を満たす候補が複数あれば Go を優先し、満たせなければ TypeScript
- D4 セキュリティ: サーバーが状態の正本を持ち、S2（正解を締切まで送らない）と S4（1人1回をサーバーで確認）を実装できる
- D5 ロックイン耐性: Go へ置き換えるときの書き直しがバックエンドの中だけで済む（フロントとのメッセージ仕様は変えない）
- D6 変更容易性: 通信方式とメッセージ仕様を基盤から切り離せる。デプロイ先を変えてもフロントの通信コードを変えずに済む

## Considered Options

- 基盤
  1. Go + Vercel Functions
  2. Go + GCP Cloud Run（Terraform で管理）
  3. TypeScript（Hono）+ Cloudflare Workers + Durable Objects
  4. Go + Fly.io
  5. Go + Cloudflare Containers
- 通信方式
  - WebSocket
  - SSE + HTTP POST
  - ポーリング

## Decision Outcome

採用する選択肢: 「TypeScript（Hono）+ Cloudflare Workers + Durable Objects、通信方式は WebSocket（Hibernation API）」。忘年会のあとに「Go + GCP Cloud Run（Terraform で管理）」へ置き換える。

理由:

- 候補3は、D1〜D3 のすべてで最も確実な選択肢だった
  - 部屋ごとの Durable Object は世界に1つだけと基盤が保証するため、部屋の状態が分断しない。Hibernation API では1オブジェクトあたり最大32,768接続を扱え、SQLite で A3 の保存先も DO の中で完結する
  - Workers Free プランで利用でき（1日10万リクエスト、13,000 GB秒、書き込み10万行）、想定の利用量でも1日数百リクエストに収まる。上限を超えるとエラーになるだけで課金されず、クレジットカードも不要
  - フロントと同じ TypeScript・Cloudflare・wrangler でそろえられ、期限内に終わる見込みが最も高い
- 候補2は要件を満たせるが、次の追加作業が40〜80時間の予算を圧迫する
  - 公式に「max-instances を短時間超えることが週に数回ある」とあり、2台目へ分断したときの同期（Firestore などで状態の正本を持つ）が必要
  - WebSocket の時間上限（最大60分）による再接続
  - GCP の課金・IAM・Terraform の初期設定
  - さらに、時間が足りずに AI に全部任せると、候補2を選ぶ理由だった学習価値が失われる。業務での GCP 知識や Go・Terraform の学習には期限がないため、忘年会のあとに自分の手で置き換えるほうが、学習と本番の確実さを両立できる
- 候補4（Go + Fly.io）は要件を満たすが、無料枠がなく、Terraform・GCP の学習価値も得られないため、置き換え先には候補2を選んだ
- 候補1は、Vercel の Go ランタイムと WebSocket がどちらもベータで、Go の WebSocket は公式ドキュメントにない。Hobby の最大実行時間300秒で接続が切れることも重なり、D1 を確実に満たせないため除外した
- 候補5は、Workers Paid（月5ドル ≒ 750円）が固定でかかり C1 を超える。要件を満たす無料の候補があるため、C2 でも正当化できず除外した
- ポーリングは、P1 を満たす0.5秒間隔だと1回の利用で約360万リクエストになり、各基盤の無料枠を超えるため除外した。SSE + HTTP POST も成り立つが、DO では Hibernation の対象が WebSocket だけのため、WebSocket を選んだ

## Consequences

- 良い影響: 部屋の状態の正本が DO に1つだけになるので、S2・S4 や得点の確定をそこにまとめられ、分断対策が要らない
- 良い影響: 無料プランは上限を超えても課金されないため、C1・C3 を構成そのもので満たせる。止めるときは Worker を削除すればよい
- 良い影響: フロントとバックエンドが同じ言語・同じプラットフォームになり、implement-issue スキルの TDD でも DO をローカルの Workers ランタイムでテストできる
- 悪い影響: 忘年会の時点では Go を使わないため、Go・Terraform・GCP の学習は忘年会のあとに回る
- 悪い影響: DO 専用の API（Hibernation、DO の SQLite）に依存するため、Go へ置き換えるときはバックエンドを書き直す必要がある
- 対応事項: WebSocket で送る JSON メッセージの仕様を、基盤に依存しない形で先に定義し、フロントとバックエンドで共有する（D5・D6 の担保。置き換え後もフロントを変えずに済むようにする）
- 対応事項: デプロイなどで接続が切れたときの自動再接続と、状態の再取得（F19）を実装する
- 対応事項: C4 として、Workers Free の使用量が上限に近づいたことを知る方法を実装時に確認し、停止手順を README に書く
- 対応事項: O2 のリハーサルで、5部屋 × 50接続の負荷をかけ、P1（1秒以内）と P3（取りこぼしなし）を実測する
- 対応事項: DB の選定とホストの見分け方の ADR では、DO の SQLite を A3 の保存先の候補として扱う
- 対応事項: 忘年会のあと、Go + Cloud Run + Terraform への置き換えを別の ADR で決め、この ADR を superseded にする。その ADR では、max-instances を超えたときの同期方式、60分ごとの再接続、課金の自動停止（予算通知 + Pub/Sub）を検討する。あわせて、フロントも Cloud Run に乗せるかを検討する
