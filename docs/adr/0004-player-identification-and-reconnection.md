# 回答者は、部屋の DO が入室時に発行する participantId と、端末が作る再接続用の秘密で見分け、秘密は localStorage に置いて WebSocket の最初のメッセージで送る

## Status

accepted

## Context

ADR 0003 で、ホストの見分け方と、ホスト用の接続からだけ進行操作を受け付ける方法を決めた。しかし、回答者がどうやって「自分は participantId X だ」と部屋の DO に示すか（S4）と、リロードや回線切れのあとに同じ回答者として戻る方法（F19）は決まっていない。前提は次のとおり。

- 部屋の状態の正本は部屋の DO の SQLite で、締切済みの得点もここに残る（ADR 0001・A3）
- 接続の attachment の形は `{ role: "host", ownerId } | { role: "player", participantId }`（ADR 0003）
- 回答者用の WebSocket の入口では Cookie を使わない（ADR 0003）
- 回答者は会員登録・ログインをしない

この ADR では次を決める。

- participantId を誰がいつ発行するか
- 再接続用の秘密を端末のどこに持ち、どう送るか
- 1問1回となりすましの拒否を、部屋の DO でどう確かめるか
- 同じ回答者が同時に複数つないだときの扱い
- 名前がかぶったときの扱い

各サービスの仕様は、2026-10-10 時点の公式ドキュメント（context7 経由を含む）で確かめた。

## Decision Drivers

- DD1 セキュリティ（S4・S3・F2）
  - 回答は接続の attachment の participantId で受け付け、メッセージに書かれた participantId は信用しない
  - participantId は参加者一覧やランキングで全員の端末に配られる前提とし、それを知っているだけでは本人として戻れない
  - 想定する相手は、URL を知る会場の参加者（開発者ツールを使える人、他人の画面をのぞく人）と、ネット全体
  - 再接続用の秘密は、試せる回数を制限しなくても総当たりで当たらない強さ（128ビット以上）にし、部屋ごとに別の値にする
  - 秘密がログ・ブラウザの履歴・リンクのプレビュー・投影画面に残らない
  - 1問1回は、部屋の DO の SQLite で確かめ、休止や再起動のあとも二重回答を拒否する
  - ホストの Cookie の権限が回答者用の接続に混ざらず、同じブラウザでホストと回答者の接続を同時に持てる
  - 部屋に入れるのは上限の50名まで（SC1）
- DD2 使い勝手（F19・F2）
  - 同じ端末・同じブラウザなら、リロード・回線切れ・タブの閉じ・開き直しのあとも、名前を入れ直さずに同じ participantId・名前・得点で戻れる。端末を替えた人は新しい回答者として入り直す
  - 再接続できるのは、部屋が終わるまで、かつ入室から6時間以内
  - 同時接続と名前のかぶりのときの動きが、回答者に分かる
- DD3 パフォーマンス（P1）: 確かめるのは接続を開くときの1回だけ。回答や進行のたびに確かめ直さず、D1 など DO の外に問い合わせない
- DD4 可用性（A3・A1）: 部屋の DO が休止・再起動・デプロイから戻っても、同じ participantId で戻れる
- DD5 変更容易性・テスト（M1・M2）: 再接続・なりすましの拒否・二重回答の拒否・同時接続の扱いを、vitest-plugin の中で外部と通信せずにテストできる
- DD6 ロックイン耐性（ADR 0001 の D5）: Go + Cloud Run へ移すときも、秘密の送り方を含めてフロントとのメッセージ仕様を変えずに済む
- DD7 運用・ランニングコスト（C1〜C4）: DO の外のサービスやアカウントを増やさない。ストレージの書き込みは入室1回につき数行程度にし、Workers Free の範囲に収める
- DD8 学習コスト・期限: ADR 0001 の40〜80時間の残りに収める。新しいライブラリやサービスが増える案ほど不利とする

## Considered Options

- 軸J: 入室の手順（participantId を誰がいつ発行するか）
  - J1. 名前を HTTP の POST で送って入室し、部屋の DO が発行した participantId と秘密を受け取ってから WebSocket を開く
  - J2. 先に WebSocket を開き、最初のメッセージ `join { name }` で入室する。部屋の DO が participantId と秘密を発行し、その接続で返す
  - J3. participantId と秘密を端末が作り、最初の入室で部屋の DO が登録する
- 軸R: 本人であることを何で示すか
  - R1. ランダムな秘密を部屋の DO が発行し、DO の SQLite にハッシュで保存する
  - R2. 署名付きのトークン（HMAC）を部屋の DO が発行し、DO は秘密を保存しない
  - R3. 名前と短い PIN
- 軸L: 端末のどこに持つか
  - L1. localStorage（部屋 ID ごとのキー）
  - L2. sessionStorage
  - L3. HttpOnly の Cookie（部屋ごとの Path）
- 軸T: どう送るか
  - T1. WebSocket の接続 URL のクエリ
  - T2. 接続後の最初のメッセージ（`resume { token }`）
  - T3. `Sec-WebSocket-Protocol` ヘッダー
  - T4. Cookie
  - T5. 秘密を HTTP の POST で送り、使い捨てのチケットを受け取って接続 URL に付ける
- 軸X: 同じ participantId で同時につながったとき
  - X1. 新しい接続を優先し、古い接続は理由付きで閉じる
  - X2. 先の接続を優先し、新しい接続を断る
  - X3. 両方を許す
- 軸N: 名前がかぶったとき
  - N1. 入室を断り、別の名前を入れてもらう
  - N2. 番号を付けて入室を許す
  - N3. そのまま許す
- 組み合わせ（比較で残ったもの）
  - 組み合わせ1: J2 + R1 + L1 + T2 + X1 + N1
  - 組み合わせ2: J1 + R1 + L3 + T4 + X1 + N1
  - 組み合わせ3: HttpOnly Cookie に秘密を置き、使い捨てのチケットを WebSocket の最初のメッセージで送る

## Decision Outcome

採用する選択肢: 「組み合わせ1（J2 + R1 + L1 + T2 + X1 + N1）の秘密を端末が作る形に変え、XSS を起こさないための多重の対策を加える」。具体的には次のとおり。

- 端末は、32バイト（256ビット）のランダムな秘密を `crypto.getRandomValues` で作り、localStorage に部屋 ID ごとに保存する
- 回答者は WebSocket を開いて `join { name, token }` を送る
- 部屋の DO は participantId を発行する。秘密は SHA-256 のハッシュにして SQLite に保存する
- 再接続のときは、最初のメッセージ `resume { token }` で秘密を送る

理由:

- R1 は DD1・DD4・DD6・DD8 で最も良い
  - 256ビットの乱数なら SHA-256 で十分で、遅いハッシュは要らない
  - SQLite に残るので、DO の再起動やデプロイのあとも同じ participantId で戻れる
  - 部屋が終わったか、入室から6時間たったかは、参加者の行を見るだけで確かめられる
  - 秘密は入室から6時間で使えなくなるので、Go へ移すときに引き継ぐ秘密のデータがない
- 秘密は、R1 のように部屋の DO が発行するのではなく、端末が作って `join` で送る
  - DO が発行すると、参加者の行を保存したあと、応答が届く前に接続が切れたときに、端末に秘密が残らない。DO はハッシュしか持たないので秘密を発行し直せず、名前も使われたままなので入り直せない。上限50名の1枠も使ったままになる
  - 端末が送る前に localStorage に保存しておけば、応答が届かなくても `resume` で戻れる
  - 秘密の強さは端末の `crypto.getRandomValues` に頼るが、弱い秘密を送って困るのはその回答者だけである。DO は長さが32バイトであることだけを確かめる
- R2（HMAC）は、トークンの形式・鍵の管理（ローカル・テスト・本番）・期限の検証を自作する必要があり、取り消しもできない。さらに、部屋の DO は得点を持つ参加者の行をもともと SQLite に持ち、部屋が終わったかも DO で確かめる。そのため「DO が秘密を保存しない」という R2 の利点が効かない
- T2 を選んだのは、秘密が URL にもログにも出ないから
  - Workers Logs は呼び出しのたびに「`<Method> <URL>`」を記録し、`observability.redactQueryString` の既定値は `false` なので、T1 ではクエリの秘密が既定でログに残る。Go に移ったあとも、Cloud Run のリクエストログで同じ対策が要る
  - T2 は秘密の受け渡しがメッセージ仕様の中だけで完結するので、DD6 で最も良い
  - 代わりに未確認の接続を扱う必要がある。ただし、attachment が `null` の接続を未確認とすれば、ADR 0003 で決めた attachment の形を変えずに済む
- J2 を選んだのは、入口が WebSocket の1本で済み（DD8）、入室も再接続も同じメッセージ仕様で表せるから（DD6）。J1 は HTTP の入口が増える
- L1 を選んだのは、リロード・タブの閉じ直し・ブラウザの再起動のあとも残り、F19 を満たすから
  - JavaScript から読めるため XSS には弱い
  - ただし、XSS が起きると、攻撃者のスクリプトは回答者のページの中で動き、開いている WebSocket から本人として回答できる。これは Cookie を HttpOnly にしても防げない
  - HttpOnly で防げるのは「秘密を持ち出して、あとで使うこと」だけで、秘密が部屋ごと・6時間で切れるこの設計では差が小さい
  - そのため、HttpOnly に頼るより、XSS そのものを起こさない対策に力を入れる
- 組み合わせ2（L3 + T4）は、XSS で秘密を持ち出されることは防げるが、XSS のあいだのなりすましは防げない
  - 回答者用の入口でも Cookie を使うので、ADR 0003 の「回答者用の入口では Cookie を使わない」を見直すことになる
  - Better Auth の Cookie も回答者用の入口に届き、権限が混ざらないかどうかが「どの名前の Cookie を読むか」というコードに頼る形に変わる
  - CSRF（CSWSH）が起きうるので、`Origin` と `SameSite` での対策が必須になる
  - Cookie を発行するために HTTP の入口が増え、フロントが「この部屋に入ったことがあるか」をサーバーに聞く手順も要る
- 組み合わせ3（Cookie + 使い捨てのチケット）は、ADR 0003 の決定を文字どおり守れるが、組み合わせ2 の CSRF 対策に加えてチケットの保存と1回だけ使える処理が増える。それでも XSS のあいだのなりすましは防げないため、作業に見合わない
- 組み合わせ1 では、秘密を自動で送る仕組み（Cookie）がない。別のサイトは localStorage を読めないので、CSRF（CSWSH）は起きない
- X1 を選んだのは、次の2点から
  - スマホの回線切れで、古い接続がまだ生きているように DO に見えていても、すぐ戻れる（DD2・A1）
  - 秘密が漏れて乗っ取られたとき、本人の画面に表示が出て気づける（DD1）
  - X3 は作りが最も小さいが、乗っ取られても本人が気づけない
- N1 を選んだのは、ランキングと最速正解者（F14）で誰のことか取り違えないから。N2 は、自分の表示名に番号が付いたことに気づきにくい
- S4 の1問1回は、どの組み合わせでも同じ形にする
  - 回答表の `UNIQUE(question_id, participant_id)` と受付中かどうかを、1つのトランザクションで確かめる
  - participantId は attachment から取る
- 外した候補と理由
  - J3: 秘密だけでなく participantId まで端末が作ると、他人と同じ participantId を名乗る登録を断る処理が増える。応答が届かなかったときに戻れるようにするには、秘密を端末が作れば足りる
  - R3: 4〜6桁は総当たりで当たり、名前は公開されているため DD1 を満たさない
  - L2: タブを閉じると消え、DD2 を満たさない
  - T3: Tail で値が置き換えられないヘッダーなので、そのままログに残りうる。サブプロトコル本来の使い方でもない
  - T5: チケットの保存と1回だけ使える処理が増え、T2 で足りる
  - X2: 古い接続が残っていると本人が戻れない
  - N3: F14 とランキングで誰のことか分からない

## Consequences

- 良い影響: 秘密が URL・ログ・履歴・リンクのプレビューに出ない。入室も再接続も WebSocket のメッセージ仕様だけで表せるので、Go へ移してもフロントを変えずに済む
- 良い影響: Cookie を使わないので CSRF（CSWSH）が起きず、ADR 0003 の決定と attachment の形をそのまま使える。ホストが同じブラウザで回答者としても参加しても（F2）、ホストの権限は回答者用の接続に混ざらない
- 良い影響: 確かめるのは `resume` を受けたときの1回だけ。その後は attachment の participantId で回答を受け付けるので、回答や進行のたびに確かめ直さない（P1）
- 良い影響: 秘密のハッシュが SQLite にあるので、休止・再起動・デプロイのあとも同じ participantId で戻れる（A3）
- 悪い影響: 秘密は JavaScript から読めるので、XSS が起きるとなりすまされる。守りは XSS を起こさない対策に頼る
- 悪い影響: 未確認の接続を扱う処理が要る
- 悪い影響: 部屋の URL を知る人が、未確認の接続を大量に開いて回答者用の上限の100本を埋めると、ほかの回答者が入れない。時間切れ（10秒）で閉じても、空いた枠にすぐ接続を開き直せば、埋めたままにし続けられる。URL を知る人だけが起こせることなので（S3）、続けて邪魔されることも受け入れる
  - ただし、ホストまで締め出されると、出題も締切も進められず部屋全体が止まる。入れない回答者が出るのとは被害の大きさが違うので、これは受け入れない。ホストの接続は回答者用の100本とは別の枠で数え、回答者用の入口からは埋められないようにする（対応事項の「1部屋の接続の上限」を参照）
  - 接続の試行の回数は制限しない。URL を知る人は、スクリプトで `join` を50回送るだけでも50名の枠を埋めたままにでき（`Origin` の対応事項を参照）、試行を制限してもこれは防げないため
  - 接続元の IP ごとに制限する案も採らない。会場の Wi-Fi では参加者が同じ IP を使うことが多く、正しい参加者まで断ってしまうため
- 悪い影響: 端末を替えた人、ブラウザのデータを消した人、プライベートブラウズのウィンドウを閉じた人は、新しい回答者として入り直す。得点は引き継がれず、元の名前は使われたままなので、別の名前にする必要がある
- 悪い影響: 同じ人が別のブラウザやプライベートウィンドウで、別の回答者としてもう1度入ることは防げない（回答者のログインはスコープ外）
- 悪い影響: 同じ部屋を2つ目のタブで開くと、先に開いていたタブの接続が閉じられる
- 対応事項: 部屋の DO の SQLite に参加者の表を作る
  - 列は participantId（`crypto.randomUUID()`）、表示名、正規化した名前、秘密の SHA-256 のハッシュ、入室した時刻
  - 正規化した名前には一意制約を付ける
  - 入室は1回につき1行の書き込みにする（DD7）
- 対応事項: 1部屋の接続の上限
  - 部屋の DO は、接続を受け付ける前（`acceptWebSocket` の前）に `getWebSockets()` の本数を数え、その接続の枠が上限に達していれば受け付けずに断る
  - 本数の確認から `acceptWebSocket` までに `await` を挟まない。`join` と同じく、間に別の接続が割り込まず、上限を超えない
  - 枠は入口ごとに2つに分ける。初めは、ホストの接続も含めて1つの枠で100本と決めた。しかし、それでは回答者用の入口から100本を埋められるとホストもつなげず、部屋全体が止まる。そこで 2026-10-12 に見直し、ホストの接続を別に数えることにした（#69）
    - 回答者用の入口の枠は100本にする。未確認の接続と、X1 で置き換える途中の古い接続を含める。回答者50名に対して約2倍の余裕を持たせ、置き換えやつなぎ直しが重なっても断られないようにする
    - ホスト用の入口の枠は5本にする。ホストの接続を開けるのは部屋の持ち主だけなので、回答者用の入口からは埋められない。ホストは1人で、PC とスマホの両方で開いたり、リロードが重なったりしても足りる本数にする
    - 回答者用の入口だけ上限を下げ（たとえば95本）、ホスト用の入口は合計100本まで受け付ける案も考えた。部屋の合計を100本に保てるが、ホストのタブが増えるほど回答者の枠が減るので採らない
    - ホストの接続を1本だけにして、X1 のように新しい接続で古いほうを閉じる案も採らない。PC とスマホで同時に進行画面を開けなくなるため
  - ホストかどうかは、接続の attachment の role で見分ける。休止のあとも残り、未確認の接続の時刻を入れるタグとも混ざらない
  - 数えるのは `readyState` が `OPEN` の接続だけにする。`getWebSockets()` は、DO が `close()` したあとも、相手が close を返すまでは `CLOSING` の接続を返す。そのまま数えると、未確認のまま閉じた接続が枠を使い続ける
  - 断られた端末は、ほかの切断と同じく、間を空けて自動で再接続する。ホストが6本目を開いたときも同じく `4503` で断る
- 対応事項: 未確認の接続の扱い
  - attachment が `null` の接続は未確認として、`join` と `resume` 以外のメッセージを拒否する
  - 受け付けてから10秒以内にどちらも来なければ閉じる。時間の値と閉じ方は次のとおりにする。Cloudflare の仕様は、2026-10-11 時点の公式ドキュメント（context7 経由）で確かめた
  - 時間は10秒にする。端末は接続が開いたらすぐに `join` か `resume` を送るので、スマホの回線で往復に数秒かかっても間に合う。未確認の接続が開いたまま枠を使うのは、1本につき10秒ほどまでになる（開き直されるときの扱いは「悪い影響」を参照）
  - 端末は、名前の入力を終えてから接続を開く（T26）。名前を入れているあいだ接続を開いたままにすると、10秒で閉じられてしまうため
  - 受け付けた時刻は、`acceptWebSocket(ws, ["acceptedAt:<ミリ秒>"])` のようにタグに入れる。タグは受け付けるときにしか付けられないが、受け付けた時刻はそのときに決まるので足りる。attachment は `null` のまま未確認を表すので、ADR 0003 とこの ADR の attachment の形は変えない。時刻を SQLite に持つ案は、接続のたびに書き込みが増え（DD7）、閉じたあとの片付けも要るので採らない
  - 閉じ方は、次の2つを組み合わせる。どちらも、attachment が `null` で、タグの時刻から10秒を過ぎた接続を `getWebSockets()` から探して閉じる
    - 部屋の DO の alarm で閉じる。予定した alarm は休止を妨げず、時間になると休止中の DO を起こす。`setTimeout` は休止を妨げ、休止すると消えるので使わない
    - 新しい接続を受け付けるとき、上限の本数を数える前にも閉じる。alarm は最大1分ほど遅れることがあるので、遅れても上限を埋められる時間を10秒ほどに抑えるため。この処理も同期の処理だけで行い、本数の確認から `acceptWebSocket` までに `await` を挟まない
  - 閉じるときの close code は `4408`、reason は `join_timeout` にする
    - 4000〜4999 はアプリが自由に使える範囲で、4000 に HTTP の状態コード（408 Request Timeout）を足した数にする。graphql-ws も、最初のメッセージが時間内に来ないときに `4408` で閉じる
    - T9 では、ほかの理由で閉じるとき（`resume` の失敗、X1 の置き換えなど）の code も同じ決まりで付け、メッセージ仕様に入れる。端末は reason ではなく code で見分ける
    - `4408` で閉じられた端末は、ほかの切断と同じく、間を空けて自動で再接続する。正しい端末がこれに当たるのは、回線がとても悪いときだけだから
- 対応事項: 未確認の接続の alarm と、T21 の締切の alarm の共用
  - 部屋の DO が持てる alarm は1つだけで、`setAlarm()` を呼ぶと前の予定を上書きする。そのため、次に起きる時刻は、締切と「一番古い未確認の接続の時刻 + 10秒」のうち早いほうにする
  - 次に起きる時刻は、`getAlarm()` で読まず、毎回、状態から計算し直す。締切は SQLite から、未確認の接続の時刻はタグから、どちらも同期で取れる。こうすると、片方の予定を上書きで消してしまうことがない
  - 計算し直して `setAlarm()` を呼ぶのは、未確認の接続を受け付けたとき、回答の受付を始めたとき（T21）、alarm の処理の最後の3か所にする。締切も未確認の接続もなければ `deleteAlarm()` を呼ぶ
  - `join` や `resume` が通っても alarm は直さない。要らなくなった alarm は1回起きて何もせずに終わるだけなので、書き込みを増やさないほうを取る
  - alarm は少なくとも1回動くことが保証され、失敗するとやり直される。そのため alarm の処理は、2回動いても結果が変わらないようにする。たとえば、すでに閉じた接続や、すでに済んだ締切には何もしない。締切の処理の中身は T21・T23 で決める
- 対応事項: `join` を受けたときの処理
  - 名前を NFKC で正規化し、前後の空白を除いてから、かぶりと部屋の上限（50名）を確かめる
  - かぶりと上限の確認から参加者の行の挿入までを、`await` を挟まない同期の SQL で行う。DO は1つのスレッドで動くので、間に別の `join` が割り込まず、50名を超えない
  - 秘密の長さが32バイトでなければ断る
  - 名前がかぶったら、理由付きで断る
  - 受け付けたら attachment に `{ role: "player", participantId }` を記録し、participantId を返す。秘密は端末が持っているので返さない
- 対応事項: `resume` を受けたときの処理
  - 秘密のハッシュを `crypto.subtle.timingSafeEqual` で比べる
  - 部屋が終わっていないことと、入室から6時間以内であることを確かめる
  - 通ったら attachment を記録し、その回答者の名前・得点と、部屋の今の状態を返す
  - 通らなければ理由付きで閉じる。端末は保存した秘密を消し、名前の入力から入り直す
  - 部屋が終わっていれば `4410 room_ended`（`join` と同じ）、秘密が合わないか6時間を過ぎていれば `4401 resume_failed` で閉じる。秘密が合わないときと6時間を過ぎたときは、端末のすることが同じなので分けない
  - `resume` は participantId を持たないので、参加者（50名まで）の全員のハッシュを `timingSafeEqual` で比べて探す。`WHERE` で引くと、比べる時間が中身で変わるため
- 対応事項: X1 の実装
  - `resume` が通ったら、`getWebSockets()` で部屋の接続をすべて取り出し、attachment の participantId が同じ古い接続を理由付きで閉じる
  - `join` のあとには行わない。`join` は participantId を新しく作るので、同じ participantId の古い接続はない（2026-10-12 の T20 で決めた）
  - 閉じたあとも、相手が close を返すまでは `getWebSockets()` に `CLOSING` として残る。そこへもう一度 `close()` を呼んでも例外にならないことを、2026-10-12 にローカルの Workers の実行環境で確かめた。回線が切れて古い接続が残ったまま、3本目の接続が来ても止まらない
  - タグは使わない。タグは `acceptWebSocket` のときにしか付けられず、J2 ではその時点で participantId が決まっていないため。1部屋の接続は、回答者用の100本とホスト用の5本までなので、すべてたどっても負担は小さい
  - 閉じられた側の端末は自動で再接続せず、「別のタブで開かれました」と表示する
- 対応事項: 回答の受け付け
  - 回答表に `UNIQUE(question_id, participant_id)` を付ける
  - 受付中かどうかの確認と一緒に、1つのトランザクションで書き込む
  - participantId はメッセージの中の値ではなく attachment から取る
- 対応事項: XSS を起こさないための多重の対策
  - CSP（`script-src 'self'` など）を設定する
  - F5 の Markdown は生の HTML を許さず、許した要素だけを描画する
  - 回答者の名前は文字として描画し、`innerHTML` 系の API を使わない
- 対応事項: 回答者用の入口でも、Worker が `Origin` を確かめる。認証のためではなく、別のサイトを開いた人のブラウザから、勝手に入室させられるのを防ぐため。`Origin` はブラウザ以外からなら自由に付けられるので、スクリプトによる大量の入室は防げない。その歯止めは部屋の上限（SC1 の50名）が担う
- 対応事項: 秘密をページの URL（アドレスバーに出る URL）に入れない。回答者がその URL を友だちに送ると、身元ごと渡してしまうため。メッセージをログに出すときも、秘密を除く
- 対応事項: vitest-plugin で次のことを自動テストで確かめる
  - 他人の participantId を名乗っても回答できない
  - 同じ問題に2回回答できない
  - 正しい秘密で戻れて、間違った秘密・部屋の終了後・6時間を過ぎた秘密では戻れない
  - 同じ participantId で2本目をつなぐと、古い接続が閉じられる
  - 名前がかぶると断られる
  - 49名のときに2件の `join` が同時に来ても、50名を超えない
  - 100本つないだ状態で、101本目の接続が断られる
  - 99本つないだ状態で2本の接続が同時に来ても、100本を超えない
  - 回答者用の入口から100本を埋めても、部屋の持ち主のホストはつなげる。ホストの接続は回答者用の100本に数えず、6本目は断られる
  - 未確認の接続から `join`・`resume` 以外のメッセージを送ると拒否される
  - 10秒を過ぎた未確認の接続が、`runDurableObjectAlarm(stub)` で動かした alarm で `4408` で閉じられる。`evictDurableObject(stub)` で休止させたあとも閉じられる
  - 未確認の接続で100本を埋めても、10秒を過ぎたあとの新しい接続は、alarm を待たずに受け付けられる
  - 締切と未確認の接続の両方があるとき、alarm が早いほうの時刻に予定される（T21）
  - `join` の応答が届く前に接続が切れても、保存した秘密の `resume` で同じ participantId に戻れる
  - `evictDurableObject(stub)` による休止と、`evictDurableObject(stub, { webSockets: "close" })` による接続の切断のあとも、同じ participantId で戻れる
- 対応事項: `join`・`resume` とその応答のメッセージ仕様は、ADR 0001 の対応事項にあるフロントとバックエンドで共有するメッセージ仕様に含める
