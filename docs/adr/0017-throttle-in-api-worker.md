# 要求の絞り込みと HTTP の守りは API の Worker に置き、守れない Workers のリクエストの枠は受け入れる

## Status

accepted

## Context

#341 の点検（2026-11-16）で、要求の数を絞る仕組みがどこにも無いと分かった（所見 S-01・Z3）。Workers Free の1日の枠はアカウント全体で分け合うので、外の誰かが要求を送り続ければ、その日の残りは画面も API も止まる（[stop-and-usage.md](../runbooks/stop-and-usage.md#1日ごとの上限)）。`*.workers.dev` には自分のゾーンが無いので、Cloudflare の WAF もレート制限のルールも付けられない。ドメインは買わないと決めている（[ADR 0003](0003-host-identification-and-host-connection.md)・[ADR 0006](0006-spa-and-api-worker-layout.md) の DD3）。

### 1日の枠と、数え方

Cloudflare の文書（Workers の料金と上限のページ、context7）で、2026-11-28 に確かめた。どれもアカウント全体の数で、毎日 0:00 UTC に戻る。

| 枠                      | 1日の上限          | 数え方                                                                                                                                     |
| ----------------------- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Workers のリクエスト    | 100,000            | 外から Worker に届いた要求。WebSocket は最初の Upgrade の1回だけで、そのあとのメッセージは数えない。Service binding の転送は足さない（注） |
| Durable Objects の要求  | 100,000            | DO への fetch・RPC、alarm が起きた回数、届いた WebSocket のメッセージ（20通で1回）。送るメッセージと ping は数えない                       |
| DO の SQLite に書いた行 | 100,000            | 書いた行と消した行。`setAlarm()` は1回で1行                                                                                                |
| D1 で読んだ行・書いた行 | 5,000,000・100,000 | 読む・書くにかかわらず、どちらかが尽きると D1 への問い合わせがすべて失敗する（ADR 0005）                                                   |
| Workers の CPU 時間     | 1回 10 ms          | 1日の上限ではなく、1回の要求ごとの上限                                                                                                     |

注: 画面の Worker が `/api/*` を Service binding で API の Worker へ転送しても、数えるのは画面の Worker の1回だけで、CPU 時間は2つの Worker の合計になる。静的ファイルの配信は数えない。この2つは ADR 0006 を書いたときと変わっていない。

### 1回の要求で使う枠

今のコードで、外から1回送ったときに使う枠を数えた。

| 操作                                                  | Workers | DO の要求                                | DO の書き込み                  | D1                                                           |
| ----------------------------------------------------- | ------- | ---------------------------------------- | ------------------------------ | ------------------------------------------------------------ |
| 回答者の接続（`/ws/play`）。join を送らずに放っておく | 1       | 2（受け付ける fetch と、10秒後の alarm） | 1（未確認の接続の `setAlarm`） | 0                                                            |
| ホストの接続（`/ws/host`）                            | 1       | 1                                        | 0                              | 読み数行（セッションと許可リスト）                           |
| 開いた接続で送るメッセージ1通                         | 0       | 1/20                                     | メッセージによる（回答は1行）  | 0                                                            |
| ログインの開始（`POST /api/auth/sign-in/social`）     | 1       | 0                                        | 0                              | 書き1（`verification`。#350 で 0 にする）                    |
| 問題セットの保存（`PUT /api/question-sets/:id`）      | 1       | 0                                        | 0                              | 書き最大約200（題名1・前の問題の削除100・挿入100）、読み数行 |
| 部屋を作る（`POST /api/rooms`）                       | 1       | 1                                        | 最大約100（問題セットの写し）  | 読み最大約100                                                |
| ログインしていない・形が違うなどで断る要求            | 1       | 0                                        | 0                              | 0〜数行の読み                                                |

ここから分かること:

- D1 の読みの枠は Workers の枠の50倍あるので、1回の要求で50行より多く読まない限り、先に尽きるのは Workers の枠になる。危ないのは、1回の要求で Workers の枠より速く減る枠、つまり **D1 か DO に1行でも書く経路と、DO を呼ぶ経路** である
- 回答者の接続は、1回で DO の要求を2回使う。5万回つなぐと、Workers の枠より先に DO の枠が尽きる
- 問題セットの保存は、1回で最大約200行を書く。約500回で D1 の書き込みの枠が尽き、その日はログインも問題セットの保存もできなくなる
- 開いた WebSocket で送るメッセージは、Worker を通らない。1本の接続から毎秒1000通送ると、DO の要求は毎秒50回ずつ増え、約33分で1日の枠に届く。Worker で絞っても、これには届かない

### Rate Limiting binding

Cloudflare の文書（Workers の Rate Limiting の binding のページ、context7、2026-11-28）で確かめたこと:

- `ratelimits` の binding を Worker に付けると、`limit({ key })` が `{ success }` を返す。設定は `simple.limit` と `simple.period` だけで、`period` は 10 秒か 60 秒しか選べない。wrangler は 4.36.0 から
- 数は Cloudflare の拠点ごとに持つ。isolate がそれぞれ手元の値で判定し、少し遅れて拠点の中の数に合う。文書も「緩く、だんだん合う。正確な数え方には使わない」と書いている
- 同じ `namespace_id` の binding は、別の Worker でも数を分け合う
- 鍵に IP を使うことは勧めていない（大勢が1つの IP を使う場合があるため）
- 無料プランで使えるかは、文書に書かれていない

#342 で、本番と同じアカウントに試験用の Worker を deploy して確かめたこと（2026-11-20、結果は #341 のコメント）:

- 無料プランで、`ratelimits` の binding を持つ Worker を deploy でき、上限を超えると `success: false` になった
- 本番の拠点では概算で、`limit: 3, period: 10` に対して数秒の間に20回ほど通った。ローカル（`wrangler dev --local`）では3回で止まり、厳密だった
- `cf-connecting-ip` は、Service binding を越えて API の Worker まで同じ値で届いた。ブラウザが自分で付けると、Cloudflare の入口が 403（error code: 1000）で止めるので偽れない。`x-forwarded-for` は、偽の値がそのまま届いた

### WAF のレート制限のルール

Cloudflare の WAF の文書（context7、2026-11-28）によると、無料プランのゾーンで使えるレート制限のルールは1つだけで、条件に使えるのは経路だけ、数える単位は IP だけ、期間と止める時間は10秒だけ。WAF は Worker より前で止めるので、止めた要求は Worker を動かさない。ただし、ゾーンを持つには自分のドメインが要る。

### Better Auth の絞り込み

better-auth 1.7.27 のソースで確かめた（2026-11-28）。

- `rateLimit.enabled` の既定は `NODE_ENV === 'production'` で決まる。Worker の実行時には `NODE_ENV` が無いので、本番でも効いていない（#342、所見 A3）
- `advanced.ipAddress.disableIpTracking: true` のとき、`getIP` は `null` を返し、rate limiter はどの要求も数えずに通す（`resolveRateLimitConfig` が `null` を返す）。ADR 0016 でこの設定を入れたので、`rateLimit.enabled: true` にしても、Better Auth の絞り込みは効かない
- 数は既定で isolate ごとのメモリに持つ。別の拠点や別の isolate には届かない

### HTTP の守り

今の API の Worker の守りは、ルートごとに付けている。

- 状態を変える Cookie の経路は、`.use(csrf(), requireHost)` を経路ごとに付ける（ADR 0003）。ただし、Hono 4.13.21 の `csrf()` は、Content-Type が form の形（`application/x-www-form-urlencoded`・`multipart/form-data`・`text/plain`）か、無いときにしか Origin を確かめない（ソースで確かめた。所見 A13）。`application/json` の要求は、`csrf()` を素通りする
- それでも今、JSON の書き込みが別のオリジンから送られないのは、2つが組み合わさっているからである。別のサイトからは、SameSite=Lax で Cookie が付かない。同じサイトの別のオリジン（同じアカウントの別の Worker など）からは Cookie が付くが、`application/json` の要求と `PUT`・`DELETE` はブラウザが先に preflight を送り、API が CORS を返さないので、本体が送られない。どちらも `csrf()` の守りではなく、CORS を足したり、JSON の経路が form の形の本文も読むようになったりすると、黙って外れる
- 本文の大きさの上限は `/auth/*` の 4 KB だけで、ほかの JSON の経路には無い（所見 A5）
- API の応答には、`X-Content-Type-Options` も `Cache-Control` も付いていない。静的ファイルの `_headers` は、Worker のコードが返す応答には付かない（ADR 0006）
- WebSocket の入口は、Cookie を読む前に `Origin` を確かめる（`ws.ts` の `requireSameOrigin`）

## Decision Drivers

- DD1 枠を守る（C1・C4）: 1台から送り続ける程度の攻撃で、D1 と DO の1日の枠が、Workers の枠より先に尽きない。どの攻撃でも、先に尽きるのは Workers の枠になる
- DD2 正しい使い方を止めない（SC1・P1）: 1つの会場の NAT（同じ IP）から、全部屋の回答者（5部屋 × 50名）が一度に入り、つなぎ直しても断られない。WebSocket のメッセージと進行操作を遅くしない
- DD3 費用（C1・C3、ADR 0003・0006）: Workers Free のまま使い、ドメインを買わない
- DD4 ロックイン耐性（ADR 0006・0008）: 画面の Worker は転送だけのまま。Go 版でも、同じ約束（どこで、何を鍵に断るか、断ったら何を返すか）を作れる
- DD5 変更容易性（M1・M2）: 鍵と上限が1か所にあり、ルートを足しても守りを付け忘れない。ちょうどの回数を、テストで確かめられる

## Considered Options

- 軸G: どこで絞るか
  - G1. API の Worker で、Rate Limiting binding を使って絞る
  - G2. 画面の Worker で、Rate Limiting binding を使って絞る
  - G3. 鍵ごとの DO で数えて、全体で正確な制限を作る
  - G4. 独自ドメインを取り、WAF のレート制限のルールで絞る
  - G5. 絞らない
- 軸K: 何を鍵にするか
  - K1. ログインの開始と部屋への接続は `cf-connecting-ip`、ホストの書き込みはセッションの `user.id`
  - K2. どれも `cf-connecting-ip`
  - K3. どれもセッションか Cookie の値
- 軸H: HTTP の守り（応答のヘッダー、非 GET の Origin の確認、本文の上限）をどこに置くか
  - H1. API の Worker の全体の middleware 1つに置き、全ルートをたどるテストで固定する
  - H2. 今のようにルートごとに付け、足りないもの（JSON の Origin の確認、本文の上限）も足す
  - H3. 画面の Worker が、転送の応答と要求に付ける

## Decision Outcome

採用する選択肢: 「G1・K1・H1」。要求の絞り込みは API の Worker に置き、Rate Limiting binding で、ログインの開始と部屋への接続は `cf-connecting-ip` を、ホストの書き込みはセッションの `user.id` を鍵に数える。部屋の DO は、接続ごとの違反の回数だけを数える。HTTP の守りは、API の Worker の全体の middleware 1つに置く。Workers のリクエストの枠は、どの案でも守れないので、受け入れたリスクにする。

- G1 を選んだ。Workers の枠はどの案でも守れない（G4 だけが守れるが、DD3 を満たさない）。それなら、Worker の1回の要求で、DO と D1 の枠が Workers の枠より速く減る経路を絞れば、どの攻撃でも先に尽きるのは Workers の枠になり、DO と D1 が先に尽きて部屋や保存だけが止まることは無くなる（DD1）。G1 はこれを、正しい要求に枠を足さずに行える
- G2 は、書き込みを user で数えられず、画面の Worker が API の経路を知ることになる（ADR 0006 の「転送だけ」の形が崩れる）
- G3 は、守りたい DO の枠を判定のたびに使い、接続も遅くなる。正確さは、上限を「桁を抑える値」として決めれば要らない
- G4 は、ドメインを買わないという判断（ADR 0003・0006）を変えることになり、無料プランのルール1つでは経路ごとの上限も作れない。ドメインを持つと決めたときに、見直す
- G5 は、DD1 を満たさない

### 軸K: 何を鍵にするか

| 軸  | 採用 | 理由と、採らなかった案                                                                                                                                                                                                                                                                                                                                                                                                 |
| --- | ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| K   | K1   | 回答者は Cookie を持たず、接続の前には名乗らないので、接続を数えられる鍵は IP しかない。ログインの開始も、ログインの前なので IP しかない。ホストの書き込みは、`requireHost` のあとならセッションの `user.id` が分かる。IP より狭く、同じ会場のほかの人を巻き込まない。K2 は、会場の NAT の数を通す値にすると、1人のホストの書き込みには緩すぎる。K3 は回答者に使えず、確かめていない Cookie の値は送るたびに変えられる |

IP は `cf-connecting-ip` だけを読む。`x-forwarded-for` は偽れるので使わない（#342）。

### 軸H: HTTP の守りをどこに置くか

| 軸  | 採用 | 理由と、採らなかった案                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| --- | ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| H   | H1   | 全体に1つなので、ルートを足しても付け忘れない。`app.routes` をたどるテストで、すべての非 GET のルートに守りがかかっていることを固定できる（`test/admin-routes.test.ts` と同じ考え方、DD5）。H2 は、ルートを足すたびに付け忘れる余地が残る。H3 は、画面の Worker が API の応答の形（403・413）を持つことになり、API だけを Go 版に替えたときに、契約テスト（ADR 0008）で Go 版が同じ守りを持つかを確かめられなくなる。画面の Worker も転送だけではなくなる |

### 決めた形

- 絞る経路と鍵（K1）
  - ログインの開始（`/api/auth/sign-in/*`）: `cf-connecting-ip`
  - 部屋への接続（`/api/rooms/:roomId/ws/host`・`/ws/play`）: `cf-connecting-ip`。`wsRoutes` で DO を呼ぶ前に数える。断るときも HTTP の status は返さず、受け入れてからアプリの close code で閉じる（`refuseConnection`、ADR 0004）
  - ホストの書き込み（`/api/question-sets`・`/api/rooms`・`/api/admin/*` の非 GET）: `requireHost` のあとで、セッションの `user.id`
  - 経路の種類ごとに別の binding（別の `namespace_id`）にし、上限を分ける。鍵には経路の種類を入れ、別の種類の数と混ざらないようにする
- `cf-connecting-ip` が無いとき（テストと、ローカルの開発）: 固定の鍵（`unknown` など）で、IP の無い要求をまとめて数える。本番では Cloudflare が必ず付けるが、万一無くても絞り込みが外れないようにする
- 上限の決め方
  - 上限は「桁を抑える値」として決め、ちょうどの回数で止まることはあてにしない。本番の拠点では、上限よりかなり多く通る（#342）
  - 1つの会場の NAT から、全部屋の回答者（5部屋 × 50名）が一度に入り、つなぎ直しても通る値にする（DD2）。その分、1台から送り続ける攻撃は止まるが、多くの IP から送る攻撃は止めきれない
  - `period` は 10 秒か 60 秒から選ぶ。値は1か所にまとめる（M2）
  - 数のちょうどを確かめるテストは、interface を差し替えた偽物か、ローカルの厳密な動きで書く。vitest-plugin の中の binding の動きは #356 で確かめる
- 数える部品の形
  - 絞り込みの middleware は、`limit({ key }): Promise<{ success: boolean }>` を持つ interface を受け取る。本番と E2E では binding を、テストでは偽物を渡す
  - binding が使えなくなったとき（無料プランから外れる、など）の代わりに、isolate の中の `Map` で固定の時間の窓を数える部品を、同じ interface の裏に作る。今は作らない。isolate ごと・拠点ごとの数になり、binding より緩いことは受け入れる
- 部屋の DO
  - DO では全体の制限を作らない（G3 を採らない）
  - 接続ごとに違反の回数をメモリで数え、決めた回数を超えたら閉じる（#354）。違反には、壊れたメッセージに加えて、短い時間に多すぎるメッセージも入れる。開いた接続のメッセージは Worker を通らないので、ここでしか数えられない。数えるのはメモリだけなので、新しく枠を使わない
- Better Auth の絞り込み
  - `disableIpTracking`（ADR 0016）のもとでは Better Auth の rate limiter は効かないので、ログインの開始の絞り込みは、この ADR の middleware で行う
  - Better Auth の `rateLimit` は、`NODE_ENV` に頼らない値を明示する（#350）。効かない `enabled: true` を書いて守っているように見せず、`enabled: false` と理由をコメントに書く
- HTTP の守り（H1）
  - API の全応答に `X-Content-Type-Options: nosniff` と `Cache-Control: no-store` を付ける
  - 非 GET・HEAD の要求は、`Origin` が要求の URL のオリジン（画面の Worker のオリジン）と同じでなければ 403 で断る。`Origin` が無い要求も断る（ブラウザは非 GET の fetch に必ず付ける。負荷試験と契約テストのクライアントも付けている）。Content-Type を問わないので、`csrf()` が見ない JSON の要求も守る
  - この確認は `/api/auth/*` にもかける。`/api/auth/*` への非 GET は、どれも画面から送る（ログインの開始とログアウト）。Better Auth 自身の確認と二重になるが、Better Auth が確かめる条件に頼らずに済む。GitHub の callback は GET なので当たらない
  - WebSocket の入口（GET の Upgrade）は、今の `requireSameOrigin` のままにする
  - 本文の大きさの上限を、全部の JSON の経路に置く。`/auth/*` の 4 KB は保つ
  - 既にある `.use(csrf(), requireHost)` は外さず、順番も変えない
  - 細かい値と、`app.routes` をたどるテストは #349 で決める

## Consequences

- 良い影響: D1 か DO に書く経路と、DO を呼ぶ経路は、DO と D1 を呼ぶ前に断られる。1台から送り続ける攻撃では、D1 と DO の枠が Workers の枠より先に尽きなくなる
- 良い影響: 開いた WebSocket で送り続ける接続は、DO が切る（#354）
- 良い影響: JSON の書き込みの守りが、CORS が無いことに頼らず、API の Worker の Origin の確認になる。ルートを足しても、全体の middleware とルート表のテストで守りが外れない
- 良い影響: ドメインを買わず、Workers Free のまま使える（ADR 0003・0006 は変えない）
- 悪い影響（受け入れたリスク）: Workers の1日10万リクエストの枠は守れない。Worker が断った要求も、それ自体が1リクエストに数えられるので、要求を送り続ければ、その日の残りは画面も API も止まる。止めたら、課金されずに 0:00 UTC（日本時間 9:00）まで待つ（C4）。脅威モデルの「受け入れたリスク」に書く
- 悪い影響（受け入れたリスク）: 数は拠点ごとの概算なので、上限を超えて通る分がある。多くの IP や多くの拠点から送られると、IP の鍵では止めきれない。会場の NAT を通す値なので、1つの IP からでも、上限までは DO と D1 の枠を使える
- 悪い影響: 同じ IP を使う大勢（会場の NAT、携帯の回線の共有の IP）は、同じ数を分け合う。会場の外の誰かが同じ IP から送り続けると、会場の回答者が断られることがある
- 悪い影響: 部屋の DO は全体の数を持たないので、多くの接続が少しずつ送るメッセージは止められない。1部屋の接続の上限（回答者用の100本、ADR 0004）と、接続の絞り込みで桁を抑える
- 悪い影響: 非 GET に `Origin` を求めるので、`Origin` を付けないクライアント（curl など）からの書き込みは 403 になる。手で API を試すときは `Origin` を付ける
- 悪い影響: Go 版（ADR 0008）は、同じ約束を Cloud Run の側で別に作る。契約テストが確かめるのは応答の形で、数の上限そのものは確かめない
- 見直す合図: 本番で実際に Workers・DO・D1 の枠が尽きたとき、ドメインを持つと決めたとき（G4 を見直す）、有料プランに移るとき、Rate Limiting binding が無料プランで使えなくなったとき（isolate の中の数え方に切り替える）、Cloudflare が `*.workers.dev` にもレート制限のルールを付けられるようにしたとき
- 対応事項（#349）: API の全体の middleware に、応答のヘッダー・非 GET の Origin の確認（`/api/auth/*` も含む）・本文の上限を置く。`test/route-guards.test.ts` で、`app.routes` の非 GET のルートをすべてたどり、よそのオリジンと `Origin` の無い要求で 403、大きすぎる本文で 413、守りがルートより先に登録されていることを確かめる。GitHub からの callback とログインが通ることを確かめる
- 対応事項（#350）: Better Auth の `rateLimit` を `enabled: false` と明示し、`disableIpTracking` のもとでは効かないことをコメントに書く。設定の形を固定するテストに入れる。ログインの開始を続けて送ると 429 になることは、#356 の middleware で確かめる
- 対応事項（#354）: 接続ごとの違反の回数に、短い時間に多すぎるメッセージを入れる。正しい端末が1回の誤りや、ふつうの速さの操作で切られないことを確かめる
- 対応事項（#356）: `apps/api/src/http/throttle.ts` に、`limit({ key })` の interface を受ける middleware を作り、この ADR の経路と鍵で数える。上限は1か所にまとめ、1つの IP から全部屋の回答者が入る場合と、E2E と負荷試験が断られないことを確かめる。vitest-plugin の中で binding が厳密に数えるかを確かめ、厳密でなければテストは偽物で書く。鍵（IP）はログに出さない。`env.e2e` にも binding を置く。手順書 `docs/runbooks/event-abuse.md` に、使用量の見方、枠が減ったときに止めるもの、部屋を終わらせること、その間は deploy しないことを書く
- 対応事項: 脅威モデルの「Workers Free の1日10万リクエストの枠」から、この ADR を指す。docs/README.md の ADR の一覧に1行足す
