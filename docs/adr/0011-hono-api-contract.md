# HTTP API は Hono のルートと、fetch + protocol の zod で呼ぶ形のまま保ち、hc と zod-openapi は使わない

## Status

accepted

## Context

ADR 0008 で、本番の API は Cloudflare（Hono + Durable Objects）に残し、Go 版は練習用の環境で作って確かめると決めた。これまでは、いずれ Go へ移るので、Hono の機能をどこまで使うかを考えずに済んでいた。本番で Hono を使い続けるので、Hono の RPC（`hc`）と `@hono/zod-openapi` を使うかを決める。

今の形は次のとおり。

- HTTP API は、`openapi.json` に載る6本（`/api/question-sets` の一覧・作成・取得・更新・削除と、`POST /api/rooms`）。ほかに `/api/health`、`/api/auth/*`、WebSocket の入口がある
- 画面は `apps/web/src/api/request.ts` の `fetch` で呼び、応答を protocol の zod で読む。そのため画面は Hono に頼らない
- サーバーの応答は `satisfies` で protocol の型に合わせている。本文の形は、画面とサーバーが同じ protocol の型を読むので、`tsc` でつながっている
- `openapi.json` は `packages/protocol/src/openapi.ts` が、zod 自身の JSON Schema（要求は input、応答は output）から書く。経路と状態の骨組みは手で書く
- ルートと `openapi.json` のずれを確かめるのは、手で直す `openapi.test.ts` の状態の表だけで、CI ではずれが見つからない。契約テストはサーバーが要るので、手元でしか動かしていない
- 状態のうち、400（`jsonBody`）・401（`requireHost`）・403（`csrf()`）はミドルウェアが返し、ハンドラーが返すのは 200・201・204・404 だけ

Hono の2つの機能は、2026-11-08 に公式の文書（context7 経由）と npm で確かめた。

| 機能                | 確かめたこと                                                                                                                                                                                                                        |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `hc`（RPC）         | サーバーの `typeof app` から型を作る。ルートはつなげて書き、状態は `c.json(..., 200)` のように書く。応答を実行時に確かめる機能はない                                                                                                |
| `@hono/zod-openapi` | 1.6.3。peer は `zod ^4.0.0` と `hono >=4.10.0`。ルートを `createRoute` と `OpenAPIHono` で書き、仕様はそこから作る。変換は zod-to-openapi が行い、v8 から zod 4 の `.meta()` を読むので、protocol のスキーマは素の zod のまま渡せる |

## Decision Drivers

- DD1 ずれの検出: ルートの経路・メソッド・状態を変えたとき、`openapi.json` や画面の呼び出しとのずれが CI で見つかる
- DD2 基盤からの切り離し: 画面は Hono にも `apps/api` の型にも頼らない。Go 版へ向けても、画面と契約テストを変えずに済む（ADR 0001 の D5・D6、ADR 0008）
- DD3 本番に入るもの: 本番の API の Worker に、仕様を配る経路や Swagger UI を入れない
- DD4 変更の量: 6本のルート・今のテスト・`openapi.json` の書き直しが小さい。同じ役割の仕組みを2つ持たない
- DD5 型のつながり: 画面が呼ぶ経路・本文・応答の型が、`tsc` の段階でサーバーとずれない

## Considered Options

- H1. 今の形を保つ。画面は `fetch` + protocol の zod で呼び、`openapi.json` は protocol の zod から書く。経路のずれは突き合わせのテスト（#240）で見つけ、Swagger UI は手元と E2E の環境だけに置く（#241）
- H2. Hono RPC（`hc`）だけ使う。ルートをつなげて書いて `AppType` を export し、画面は `hc<AppType>` で呼ぶ。`openapi.json` は今のまま
- H3. `@hono/zod-openapi` で OpenAPI だけ作る。ルートを `createRoute` と `OpenAPIHono` で書き直し、`openapi.json` をルートから作る。画面は今のまま
- H4. H3 に加えて、画面は `hc` で呼ぶ

## Decision Outcome

採用する選択肢: 「H1」。今の形を保ち、経路のずれは #240 のテストで見つける。

4つの案を DD1〜DD5 で比べた。

|                        | H1 今の形                                                                                                                          | H2 RPC だけ                                                                                   | H3 zod-openapi で OpenAPI だけ                                                                                                                                     | H4 zod-openapi + RPC |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------- |
| DD1 ずれの検出         | 経路とメソッドは #240 で CI が見つける。本文は protocol の同じ zod を使うので起きない。状態は手で直す表だけで、CI では見つからない | 画面とルートのずれは `tsc` で見つかる。`openapi.json` とのずれは今と同じで見つからない        | 経路・メソッド・本文と、ハンドラーが返す状態は起きないか `tsc` で落ちる。ミドルウェアの 400・401・403 は手で書くので、CI では見つからない                          | H3 と同じ            |
| DD2 基盤からの切り離し | 画面は protocol だけを読む。Go 版へ向けても、同じ zod と契約テストで確かめられる                                                   | 画面が `apps/api` の型に頼る。Go 版へ向けると型が実物と合わなくなるので、zod の検証は外せない | 画面は変わらない。protocol は素の zod と `.meta()` のままでよい                                                                                                    | H2 と同じ            |
| DD3 本番に入るもの     | 変わらない                                                                                                                         | `hc` は画面だけに入り、API の Worker は変わらない                                             | `/doc` を配らなくても、`OpenAPIHono` と、仕様を組み立てる zod-to-openapi が本番の Worker に入る                                                                    | H3 と同じ            |
| DD4 変更の量           | テストを1つ足す                                                                                                                    | 6本をつなげて書き直す。`hc` の型と応答の zod の検証という、同じ役割を2つ持つ                  | 6本と `jsonBody` を書き直す。`openapi.json` の作り手が zod の `toJSONSchema` から zod-to-openapi に替わり、`openapi.json`・`openapi.test.ts`・契約テストを読み直す | H2 と H3 を足した量  |
| DD5 型のつながり       | 本文は protocol でつながる。経路の文字列はつながらない                                                                             | 経路・本文・状態まで `tsc` でつながる                                                         | H1 と同じ                                                                                                                                                          | H2 と同じ            |

理由:

- H2・H4 は DD2 を満たさない。`hc` の型は TypeScript のサーバーの型なので、ADR 0008 のように接続先を Go 版へ切り替えると、型は通っても実物とずれる。それを防ぐには応答の zod の検証を残すことになり、`hc` と zod が同じ役割を2つ持つ（DD4）
- H3 が H1 より多く防げるのは、ハンドラーが返す状態（200・201・204・404）のずれだけだった。400・401・403 はミドルウェアが返すので、H3 でも手で書く。その差のために、6本の書き直し、`openapi.json` の作り手の交代、本番の Worker への依存の追加を払うのは見合わない（DD3・DD4）
- H1 は、#240 のテストを足せば経路とメソッドのずれを CI で見つけられ、DD2・DD3・DD4 では最も良い。ルートが6本なので、状態の手書きも目で追える量にとどまる

## Consequences

- 良い影響: 画面は今のまま protocol だけに頼り、Hono にも `apps/api` にも頼らない。Go 版へ向けても、画面と契約テストを変えずに確かめられる
- 良い影響: 本番の API の Worker に入るものは変わらない。仕様の正本は、`ws.schema.json` と同じく `packages/protocol` に置いたまま
- 悪い影響: ハンドラーが返す状態と `openapi.json` のずれは、CI では見つからない。手で直す `openapi.test.ts` の表と、手元で動かす契約テストに頼る
- 悪い影響: 画面が呼ぶ経路の文字列は `tsc` で確かめられない。画面のテストと E2E で拾う
- 対応事項: ルートと `openapi.json` の経路とメソッドを、両方向に突き合わせるテストを作る（#240）
- 対応事項: Swagger UI は E2E の入口にだけ置き、本番のバンドルに入らないことをテストで確かめる（#241）
- 対応事項: 次のどちらかが起きたら、H3 へ移るかを別の ADR で決め直す。① ルートの状態と `openapi.json` のずれが、CI を抜けて E2E・契約テスト・本番で初めて見つかった ② ハンドラーが 200・201・204・404 のほかの状態（409・422 など）を返すルートができた
- 対応事項: 別の ADR で本番を Go 版に切り替えないと決め、Go 版の練習環境もやめて、画面が TypeScript のサーバーだけを呼ぶと決まったら、H2・H4 を見直す。そのときは応答の zod の検証を外し、同じ役割を2つ持たない
