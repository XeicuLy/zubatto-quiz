# ホストは Better Auth の GitHub ログインと許可リストで見分け、部屋の DO はホスト用の入口で開いた接続からだけ進行操作を受け付ける

## Status

accepted

## Context

S1 では、ホスト以外は管理画面を開けず、進行操作もできないこと、各ホストが自分の問題セットと部屋だけを操作できることを求めている。ADR 0002 で、問題セットは D1 に `owner_id` ごとに保存し、読み書きの層では `owner_id` を必須にすると決めたが、`owner_id` に何を入れるか、ホストをどう見分けるかは決まっていない。さらに、ホストは同じ URL から回答者としても参加できる（F2）ため、同じ人が部屋の DO に「ホスト用の接続」と「回答者用の接続」を両方持つことがあり、進行操作（出題・受付開始・締切）をホスト用の接続からだけ受け付ける方法も必要になる。想定するのは、知り合いのホスト1〜2名（1年後に5名程度、全員が GitHub アカウントを持つ）で、PC で問題を作りスマホで進行することがあり、使うのは年に数回である。回答者の見分け方（S4・F19）は対象外とする。各サービスの仕様・無料枠は、2026-10-10 時点の公式ドキュメント（context7 経由を含む）で確かめた。

## Decision Drivers

- DD1 セキュリティ（S1）: ホストでない人（参加用 URL を知っている人を含む）は管理画面の API と進行操作を実行できない / 要求ごと・接続ごとにサーバー側でどのホストかを決め、`owner_id` で問題セットと部屋を絞れる / 部屋の DO は、その部屋の持ち主がホスト用として開いた接続からしか進行操作を受け付けない / ホストの秘密が、回答者の端末・参加用 URL・進行画面の URL に出ない（投影されてもなりすましに使えない） / 会場の参加者とネット全体を想定し、総当たりに強い
- DD2 使い勝手・運用: 複数の端末で同じホストとして使える / 数ヶ月使わなくてもホスト本人が入り直せる。秘密を忘れたり端末を失くしたりしたときは、開発者に頼んで戻せればよい / 本番の約2時間とその前の準備の間に、ログインが切れない / ホストの追加・削除・取り消しは、開発者がコマンドで数分で行えればよい（管理画面は作らない）
- DD3 運用・ランニングコスト（C1〜C4）: ホストが5名でも無料で使える。カード登録が要らない。上限を超えても課金されない
- DD4 変更容易性・テスト（M1・M2）: vitest-pool-workers の中で外部の通信なしにテストでき、CI でも通る。テストのための抜け道は、構成上、本番で使えない
- DD5 ロックイン耐性（ADR 0001 の D5）: Go + Cloud Run へ移すとき、`owner_id` の値をそのまま使え、見分け方の作り直しがないか小さい。あとから Google のログインを足すときも、作り直しが小さい
- DD6 学習コスト・期限: ADR 0001 の40〜80時間の残りに収まる。Cloudflare 以外のアカウントや SDK が増えるほど不利とする
- DD7 パフォーマンス（P1）: 確かめるのは接続を開くときの1回だけにし、進行操作のたびに D1 や外部サービスへ問い合わせない

## Considered Options

- 軸H: ホストをどう見分けるか
  - H1. ホストごとの秘密 URL
  - H2. ホストごとの合言葉（D1 にハッシュで保存）
  - H3. GitHub の OAuth と許可リスト: 自分で実装する（H3a）/ Better Auth を使う（H3b）
  - H4. Cloudflare Access（Zero Trust の無料プラン）
  - H5. メールのログインリンク（Cloudflare Email Service）
  - H6. パスキー（WebAuthn）
- 軸I: `owner_id` に何を入れるか
  - I1. 自分で発行する ID（外部の ID とは別の列で対応づける）
  - I2. 外部の ID（GitHub のユーザー ID やメールアドレス）をそのまま
- 軸W: 部屋の DO で、ホスト用の接続をどう見分けるか
  - W1. Cookie で確かめ、ホスト用と回答者用で WebSocket の入口を分ける
  - W2. 使い捨てのチケットを接続 URL に付ける
  - W3. 接続後の最初のメッセージでトークンを送る

## Decision Outcome

採用する選択肢: 「Better Auth で GitHub ログインと許可リストを実装し（H3b）、`owner_id` には Better Auth が発行する `user.id` を入れ（I1）、部屋の DO はホスト用の入口で Cookie を確かめて開いた接続からだけ進行操作を受け付ける（W1）」。

理由:

- H3 は DD1・DD2 で最も良い。パスワード・2段階認証・総当たり対策を GitHub に任せられ、どの端末でも、数ヶ月ぶりでも GitHub でログインし直せる。GitHub OAuth App は無料でカードも要らない（DD3）
- H3b を H3a より選んだのは、DD6 と DD5（Google の追加）で上回るから
  - 開発者の別のリポジトリ（sprout-app）で、Better Auth + GitHub ログイン + Workers + D1 + Hono の構成がすでに本番で動いており、作り（`createAuth`・ログイン確認のミドルウェア・E2E のヘルパー）を流用できる。見積もりは H3a の10〜15時間に対し、4〜6時間程度
  - Google をあとから足すときは、設定の追加とアカウントのリンクで済む
  - テストは `testUtils` プラグインで、ユーザーとログイン用の Cookie をテストの中で作れる。テスト専用の auth インスタンスにだけ入れる方法が公式に推奨されている
  - 代わりに、Better Auth は TypeScript 専用なので、Go へ移すときは OAuth とログイン状態の管理を書き直す（DD5 で H3a にやや劣る）
- I1 を選んだのは、Google を足しても、ログイン方法を替えても、Go へ移しても `owner_id` が変わらないから。Better Auth の `user.id` は、GitHub のユーザー ID とは別に発行され、`account` テーブルで対応づけられるので、そのまま I1 になる
- W1 を選んだのは、DD6・DD7 で最も小さいから。D1 を読むのは接続を開くときの1回だけで、役割は DO の WebSocket attachment に残るので、休止（Hibernation）のあとも進行操作のたびに確かめ直す必要がない。Cookie を付けて WebSocket を開くのは標準的な方法なので、Go でも同じ形にできる。workers.dev では Public Suffix List に載っているのが `workers.dev` なので、同じアカウントの Worker 同士は同じサイトになり、SPA と API を同じ Worker にしても別の Worker に分けても W1 は成り立つ
- H1（秘密 URL）は、作りは最も小さいが、期限のない秘密がチャットやブラウザの履歴に残り、チャットのリンクのプレビュー対策も要る。DD1・DD2 で H3 に劣る
- H2（合言葉）は、人が決める合言葉は推測されやすいので、試せる回数の制限を自作する必要がある。Workers の Web Crypto は PBKDF2 の反復が10万回までで、ハッシュを強くするのにも限りがある。数ヶ月使わないと忘れやすく、DD1・DD2・DD6 で H3 に劣る
- H4（Cloudflare Access）は、Zero Trust の無料プランでも登録時に支払い情報の入力が必要で、DD3 を満たさないため除外した。また、Cloud Run の前に置くには Cloudflare を通る自分のドメインが要り、使わないならホストの見分け方を作り直すことになる（DD5）。なお、ローカルでは wrangler の `access.dev` で模擬でき、この設定は `wrangler dev` と Vite プラグインでしか効かないため、抜け道は構成上、本番に残らないことは確かめた。ただし、vitest-pool-workers での扱いは公式に書かれていない
- H5（メールのログインリンク）は、Workers Free では任意の宛先に送れない。無料の「確認済みの宛先」への送信も、Email Routing を設定した自分のドメインが要り、ドメインの購入が必要になるため、DD3 を満たさず除外した
- H6（パスキー）は、作業時間が最も大きい（12〜20時間）。パスキーはドメインに結びつくので、Cloud Run で別のドメインに移ると全員が登録し直すことになる（DD5）。GitHub 自体がパスキーでのログインに対応しているので、H3 を選べばパスキーの強みは GitHub 側で得られるため除外した
- I2（外部の ID をそのまま）は、Google を足すと同じ人が2つの `owner_id` を持つことになり、問題セットのデータを書き換える必要が出るため除外した
- W2（使い捨てのチケット）は、チケットの保存と1回しか使えないようにする処理が増え、W1 で足りるため選ばなかった。W3（最初のメッセージで確かめる）は、トークンを JavaScript から読める場所に置くことになり XSS に弱く、確かめる前の接続の扱いも要るため除外した

## Consequences

- 良い影響: パスワード・2段階認証・パスキー・総当たり対策を自分で作らずに済み、ホストの秘密が URL や画面に出ない
- 良い影響: `owner_id` が自分で発行する ID なので、Google の追加・ログイン方法の変更・Go への移行で、問題セットのデータを書き換えずに済む
- 良い影響: 部屋の DO は接続を開くときに1回だけ確かめればよく、本番中の進行操作に D1 への問い合わせが入らない（P1）
- 悪い影響: 許可リストの確認を忘れると、GitHub のアカウントを持つ誰でもホストになれる。S1 は、許可リストの確認とクエリごとの `owner_id` の絞り込みの2つで守ることになる
- 悪い影響: GitHub OAuth App を、ローカル用と本番用で2つ管理する必要がある（コールバック URL が違うため）。Client Secret と Better Auth の秘密鍵も管理する
- 悪い影響: GitHub から戻ってくる処理（コールバック）は、GitHub との通信をモックしないとテストできない
- 悪い影響: Better Auth は TypeScript 専用なので、Go へ移すときは、OAuth とログイン状態の管理を書き直す（テーブルの構造とデータは引き継ぐ）
- 悪い影響: GitHub のアカウントを失くしたホストは、新しいアカウントで別のホストとして始める。古い問題セットは引き継がれない
- 悪い影響: Cookie を使う WebSocket には、別のサイトから接続を開かれる攻撃（CSWSH）が残るため、接続を開くときの `Origin` の確認が欠かせない
- 対応事項: 許可リスト（GitHub のユーザー ID）を持ち、Better Auth の `databaseHooks` で、新しく登録するときとログインするとき（セッションを作るとき）の両方で確かめる。外したホストが入り直せないようにするためで、許可リストの外の人が拒否されることを自動テストで確かめる。追加・削除は wrangler のコマンドで行い、取り消すときは許可リストから外したうえで、そのホストのセッションを D1 から消す。取り消しが効くのは次の接続からで、つながったままのホスト用の接続は閉じるまで進行操作を続けられる（部屋の DO は接続を開くときに1回だけ確かめるため。P1）。すぐに止めたいときは、その部屋を終えるか Worker を削除する。手順は README に書く
- 対応事項: テストでは、`testUtils` をテスト専用の auth インスタンスにだけ入れるか、D1 にセッションを直接入れる。E2E 用のログインの入口が必要なら、本番の入口ファイルからは import されないテスト専用の入口にだけ置く。sprout-app のように、本番のコードに入口を含めて実行時の `APP_ENV` で止める方式は採らない
- 対応事項: 部屋の DO への WebSocket は、ホスト用と回答者用で入口を分ける。ホスト用の入口では、Worker が `Origin` を確かめ、Cookie のセッションから `owner_id` を決めて DO に渡す。DO は、それが部屋の持ち主と一致したときだけ、接続の attachment に `{ role: "host", ownerId }` を記録する。進行操作は、attachment の role が host の接続からだけ受け付ける。回答者用の入口では Cookie を使わない。同じ人の回答者用の接続から進行操作を送っても拒否されることを、自動テストで確かめる
- 対応事項: Cookie の `SameSite` の値は、GitHub から戻ってくる処理と合わせて実装のときに決める
- 対応事項: SPA と API を同じ Worker にするか分けるかは、この ADR では決めない。分ける場合は、Better Auth の `crossSubDomainCookies` と、Cookie を送る CORS の設定が要る
- 対応事項: Better Auth のログインの有効期限は7日（使っていれば1日ごとに延びる）とし、本番中に切れないようにする。期限が切れたら GitHub でログインし直す
- 対応事項: attachment の形（`{ role: "host", ownerId } | { role: "player", participantId }`）は、回答者の見分け方（S4・F19）の ADR でも同じものを使う
- 対応事項: Go + Cloud Run への置き換えの ADR で、GitHub ログインとログイン状態の管理を `golang.org/x/oauth2` などで書き直す手順と、Better Auth のテーブル（user・account・session）から移す手順を検討する
