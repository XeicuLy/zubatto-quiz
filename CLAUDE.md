# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

ズバッとクイズ (ズバクイ) is a real-time multiple-choice quiz app where players score on both correctness and answer speed. The repo is **early in implementation**: it holds tooling, CI and design documents. The pnpm workspace (`apps/*`, `packages/*`, `tools/*`) is set up. The packages so far are `packages/protocol` (the WebSocket message spec and the HTTP request and response shapes), `packages/scoring` (score and ranking calculation), `tools/docs-check` (tests that keep README and `docs/runbooks/` in step with the repo), `tools/loadtest` (the O2 rehearsal bots: rooms × bots play a whole game and P1, P3 and P4 come out as a Markdown table), `apps/api` (the API Worker: Hono with `GET /api/health`, the question-set HTTP API under `/api/question-sets`, `POST /api/rooms`, the room DO with its SQLite schema, an `initialize` RPC, the WebSocket entries `/api/rooms/:roomId/ws/host` and `/ws/play`, the `join` and `resume` handlers with the unverified-connection timeout and X1 replacement, the host progression commands with the answer deadline, `wrangler.jsonc` and the drizzle D1 schema with its migrations) and `apps/web` (the SPA skeleton: TanStack Router routes, Tailwind tokens, the CSP, the Worker that forwards `/api/*`, and `src/realtime`: the room WebSocket client with auto-reconnect and `resume`, the zustand room store and an in-memory fake WS server for tests; `/r/$roomId` with the player join form, waiting room, connection notices, and the question and answer screen; `/login` and `/admin` with the host's GitHub login, the question-set list and the question-set editor; `/rooms/$roomId/host` with room creation from the list, the host's lobby and the progression screen), and `e2e/` (one Playwright run through the whole game against a production-like build, with a test-only login entry in `apps/api/test/e2e-entry.ts`). Before you design or implement anything, read the documents below. They are the source of truth:

- `docs/requirements/zubatto-quiz.md` is the requirements spec. Requirement IDs are `F*` (functional), `P*` (performance), `S*` (security), `A*` (availability), `SC*` (scalability), `M*` (maintainability), `C*` (cost) and `O*` (operations). ADRs and commits cite these IDs.
- `docs/adr/0001`–`0007`, `0009` and `0010` record the accepted architecture decisions (`0008` is reserved for #146). 0007 decides UI parts: shadcn/ui on Base UI (Radix's Dialog injects a `<style>` the CSP blocks on every open; checked on `e2e:serve` 2026-10-29), shadcn's token names (`background`/`foreground`, `primary`/`primary-foreground`, `ring`…) with the stage surface swapping the values, Digital Agency design system values as the reference for type, contrast and the focus ring, and the `@/*` alias in `apps/*` only (`packages/*` are read as source, so they stay relative). 0009 decides releases: release-please's release PR sets the version, tag and Release; production is tracked by the `production` Deployments and deployed only after a Required reviewers approval. 0010 replaces part of 0005 and 0009: `release: published` starts deploy.yaml on the tag's commit with target `all`, `v*` tags can be created only by the release-please App (tag ruleset), production allows `v*` tags, the production jobs merge into one so a run needs one approval, and `verify-ci` checks the tag's commit is on `main` and waits for its CI. The tag ruleset and production's `v*` policy are in the runbooks (#170). Each ADR's "対応事項" list under Consequences is effectively the implementation checklist.
- `docs/architecture/backend.md` explains how the API Worker, the room DO, protocol and scoring work and where each rule is enforced, in Japanese. The promises below link to its sections; when you change a rule, update both.
- `plan.md` holds the original rough idea, including the frontend stack: React + TanStack Start as an SPA with `ssr: false`, TanStack Query, and zustand if needed. Where it conflicts with the requirements or ADRs, those win. TanStack Start was dropped for TanStack Router alone, because its SPA shell needs inline scripts that break `script-src 'self'` (ADR 0006). `memo.md` is a gitignored scratch file.

## Commands

```sh
make setup          # mise install (node/pnpm/uv/shellcheck pinned in .mise.toml) + pnpm install --frozen-lockfile
make check          # everything CI runs: fmt:check, lint, tsc, test
pnpm run fmt        # oxfmt (printWidth 120, single quotes, sorted imports/Tailwind classes/package.json)
pnpm run fmt:check
pnpm run lint       # oxlint --deny-warnings over the whole repo (.oxlintrc.json), then shellcheck .github/scripts/*.sh (pinned in .mise.toml)
pnpm run tsc        # root tsc --noEmit, then each package's own `tsc` script
pnpm run test       # vitest run; root vitest.config.ts bundles apps/*, packages/* and tools/* as projects
pnpm exec vitest run --project <name>   # one package; the project name is its vitest config `name`, else its package.json `name`, else its directory name
make e2e            # pnpm run e2e (Playwright, e2e/); first run needs `pnpm exec playwright install chromium`
mkdir -p logs && pnpm -s run logs:api >> "logs/api-$(date +%Y%m%d-%H%M%S).json"   # O1 backup: wrangler tail --format json of zubakui-api (also logs:web); keep the files 7 days after the last entry (O1)
```

- A Claude Code PostToolUse hook runs `oxfmt` on every file after Edit/Write, so don't format by hand.
- `.npmrc` sets `save-exact=true`, so dependencies are pinned to exact versions.
- CI (`.github/workflows/ci.yaml`) runs the same four checks on every PR to `main` and every push to `main` in the `ci` job, and the Playwright E2E in the `e2e` job. `pr-title.yaml`'s `pr-title` job lints the PR title (also on `edited`, so it isn't in `ci.yaml`) and, on a push, the `main` commit message. The `main` repository ruleset requires all three (GitHub Actions only) and has no bypass actors, so not even admins can merge a failing PR. Keep those job names. A required check's workflow must run on both PRs to `main` and pushes to `main`, because `verify-ci` looks for it on the `main` commit; `main-ruleset.test.ts` checks this across `.github/workflows/`. `ci-workflow.test.ts` also fails any `run:` that embeds `github.event.*` or `github.head_ref` in `${{ }}`; pass such values through `env:`.
- Each package's `tsconfig.json` extends `tsconfig.base.json` and adds its own `types`/`lib`. A package with a `tsc` script is type-checked by the root `pnpm run tsc`.
- vitest 4 fails with "No projects were found" when no project glob matches, so `vitest.config.ts` leaves `projects` unset while `apps/`, `packages/` and `tools/` are empty. `@cloudflare/vitest-pool-workers` is deprecated and renamed to `@cloudflare/vitest-plugin`, which supports vitest 4 and 5 (checked 2026-10-11).
- oxlint rejects `dangerouslySetInnerHTML`, `innerHTML`-style DOM APIs (ADR 0004) and imports of test code (`test/`, `*.test.*`, `*.spec.*`) from production code. Test code may import production code.
- oxlint's `jsx-a11y` plugin is on (its `correctness` rules, except `prefer-tag-over-role`: `<output>` and `<img>` don't fit a `role="status"` `<p>` or an inline `<svg role="img">`). Move initial focus with a ref and `useLayoutEffect`, never `autoFocus` (`no-autofocus`). A false positive gets `// oxlint-disable-next-line <rule>` with the reason on the line above (`autocomplete="nickname"`, an `alertdialog` catching a bubbled Esc).

## Commits

- Commitlint enforces Conventional Commits through a husky `commit-msg` hook. The type is in English and the subject is in plain-form Japanese, for example `docs: 1部屋の WebSocket 接続に100本の上限を設ける`.
- PRs are squash-merged only (ADR 0009), with the squash body blank, so **the PR title becomes the commit on `main` and its CHANGELOG line**. `pr-title.yaml` checks it with the same commitlint config. Only `feat`/`fix`/`perf` reach the CHANGELOG and bump the version; mark a breaking change with `!` in the title. Commits inside a PR are still split (code and docs apart) for review.
- Don't mention the target event or its deadline in commit messages.
- `.claude/settings.json` denies `git reset`, `git rebase` and `git rm`.

## Planned architecture (from the ADRs)

The first release is all TypeScript on Cloudflare's free plan. After the first event, the backend will be rewritten in Go on Cloud Run with Terraform (ADR 0001). Keep backend platform specifics out of anything the frontend depends on. In particular, the **WebSocket JSON message spec must be platform-independent and shared between frontend and backend**, so the rewrite doesn't touch the frontend.

- **Backend** (`apps/api`, `packages/protocol`, `packages/scoring`): the reasons, file names and test helpers are in [docs/architecture/backend.md](docs/architecture/backend.md). Keep these promises:
  - [Shape](docs/architecture/backend.md#全体の形): one Hono Worker plus one Durable Object per room (Hibernation API + DO SQLite), the single source of truth. No polling or SSE. Every path is under `/api/` on one origin, with no CORS (ADR 0006). Don't deploy `apps/api` during an event.
  - [Question sets](docs/architecture/backend.md#問題セットと部屋を作る): every D1 access takes `owner_id`, and another host's set or room looks missing (404, 4404) (S1). Rooms use `newUniqueId()`, never `idFromName` (S3), and copy the set in one `transactionSync`; play never reads D1. Cookie routes that change state use `.use(csrf(), requireHost)`, `csrf()` first.
  - [WebSocket entry](docs/architecture/backend.md#websocket-の入口): check `Origin` before any cookie, never forward the browser's request to the DO (`roomRequest`), and register `wsRoutes` before `roomRoutes`. Never refuse a browser's WebSocket with an HTTP status: accept it and close with an app code (`refuseConnection`).
  - [Host auth](docs/architecture/backend.md#ホストの認証): check the allowlist in `user.validateUserInfo` (before any row is written; `account.create.before` would leave a `user` row) and again in `session.create.before`. `testUtils` goes only in the test-only auth.
  - [Progression](docs/architecture/backend.md#進行の操作): host commands only from host-role sockets, in protocol's `transition` order. `handleHostCommand` and `handleAnswer` call `closeAnsweringIfDue` first ([why](docs/architecture/backend.md#締切と採点)).
  - [S2](docs/architecture/backend.md#結果と送り直し): correct answers never leave the DO before the deadline. Outside `initialize`, only `scoreQuestion` and `results.ts` read `correct_index`. Results are never stored; they are rebuilt with a fixed number of queries (P4). Send only through `room/send.ts`: `broadcast` skips unverified sockets, and `answerProgress` goes only to hosts (`sendToHosts`).
  - [Players](docs/architecture/backend.md#回答者の参加とつなぎ直し): the secret goes only in the first WS message, never a URL or log; the DO keeps its SHA-256 and compares with `timingSafeEqual`, never `WHERE token_hash = ?`. `participantId` comes from the attachment, never the body, and a `null` attachment may send only `join`/`resume`. After an `await` (`hashToken`), re-check `OPEN` and the attachment.
  - [Concurrency](docs/architecture/backend.md#同時に起きる処理の約束): count against the cap before `acceptWebSocket` with no `await` in between (players 100 and hosts 5, counted apart). The `join` checks and insert are synchronous SQL. One answer per question is `UNIQUE` plus the accepting check in one `transactionSync`, with `ON CONFLICT … DO NOTHING`, never `INSERT OR IGNORE`.
  - [Messages](docs/architecture/backend.md#メッセージの形): decode with `decodeClientMessage` and send with `encodeServerMessage`. A field added to a server message gets a `.default()`. After a schema change, run `pnpm --filter @zubatto-quiz/protocol run schema` (`ws.schema.json` is the source of truth for the Go rewrite).
  - [D1](docs/architecture/backend.md#d1-のスキーマ) and [room SQLite](docs/architecture/backend.md#部屋の-do-の-sqlite): migrations come from `db:generate`, are never edited by hand and stay additive once deployed; never edit a deployed `ROOM_MIGRATIONS` version. Room SQL uses `ctx.storage.sql` (no drizzle) and binds every value with `?`.
  - [Scoring](docs/architecture/backend.md#採点の関数): points and ranks come only from `packages/scoring`. Change values only in `config.ts` (M2), and normalize each elapsed time once with `normalizeElapsedMs` (P2).
- **XSS hardening** replaces HttpOnly here:
  - CSP `script-src 'self'`, set in `apps/web/public/_headers`. Keep `apps/web/index.html` free of inline scripts, styles and event handlers; a test checks both files. `_headers` applies to `vite build`/`vite preview`/deploy but not `vite dev`, and never to Worker responses (`/api/*`).
  - Question text is plain text too. F5 was Markdown and became newlines only (#44): `whitespace-pre-line` on every element that shows `question.text`, so no user input is ever turned into elements.
  - Never use `innerHTML`-style APIs for user-provided names.
- **Infra** (ADR 0005): `wrangler.jsonc` is the only IaC. It holds the Worker, the DO `new_sqlite_classes` migration and the D1 binding.

When a change affects one of them (a secret, a table, a command, the CI job name), update the runbook in the same change.

A `GITHUB_TOKEN`-made PR would leave ci/e2e waiting for approval. It keeps the release PR `chore: vX.Y.Z をリリースする` up to date; merging it tags that commit `vX.Y.Z` and creates the GitHub Release, which starts deploy.yaml (ADR 0010); release-please itself never deploys, and a `GITHUB_TOKEN`-made Release wouldn't start a workflow. A PR body's `BEGIN_COMMIT_OVERRIDE` is read from the first occurrence of that word, so never write it in the body's prose (#164's release PR came out empty that way). With merge commits, release-please's `splitMessages` also reads the PR title in the merge commit body, so every change appeared twice; that is why merges are squash-only.

The workflow-level `env.TARGET` is `github.event_name == 'release' && 'all' || inputs.target`: a `release` event has no `inputs`, and the explicit event check keeps an empty dispatch input from turning into `all`. A Release run checks out the tag's commit (`GITHUB_SHA`) and uses that commit's deploy.yaml, so a dispatch on an old tag (rollback) runs the old workflow. The jobs are `verify-ci` → `deploy`. `deploy` is the only job with `environment: production`, the only place the Cloudflare token and account ID live, and runs the steps migrations → API → web; the migration and API steps have `if: env.TARGET == 'all'`, and a failed step skips the rest (step-level `if` without a status function is `success() && …`). The Environment allows only the `main` branch and `v*` tags (`deployment-branch-policies`, `type: tag` for `v*`; `docs/runbooks/deploy.md`). `production` has Required reviewers (the owner, `prevent_self_review: false`, `can_admins_bypass: false`; ADR 0009), and approval is asked per job using `production` (checked 2026-10-27 with the old three-job `all`; the docs don't say), so one job means one approval (ADR 0010's E3). Don't split `deploy` back into jobs, and don't replace the reviewers with a gate job: that would take them off the Environment that holds the token. Rejecting deploys nothing; **Re-run failed jobs** reruns the whole `deploy` job (migrations are skipped when applied), so a web-only redeploy is a new `web` dispatch. During an event, don't merge the release PR; if it was merged, reject its run and later **Re-run all jobs**. `timeout-minutes` is 30 for `deploy` and 35 for `verify-ci`. `concurrency` keeps GitHub's default single pending run (a newer run cancels the pending one, and the runbook says to re-run a cancelled `all` or Release run; a Release run waiting for approval probably holds the slot, #172); don't add `queue: max`, whose order isn't guaranteed, so an older commit could deploy last. Steps call root `db:migrate:remote`/`deploy:api`/`deploy:web`; the API ones pass `--env=""`, and web's `deploy` is `vite build && wrangler deploy`.
  - `verify-ci` (`permissions: contents: read, checks: read`, no Environment, no secrets) sparse-checks out `.github/scripts/verify-required-checks.sh` and `main-ruleset.json`. The script first checks the commit is on `main` with `gh api repos/…/compare/main...$GITHUB_SHA --jq .status` (`identical` or `behind` passes; `ahead`/`diverged` fails), so no full-history checkout is needed. Then it polls every required check in the ruleset (`ci`, `e2e`, `pr-title`, filtered by its `integration_id` as `app_id`; newest check run on `GITHUB_SHA`) every `CI_POLL_SECONDS` (30) until all are `completed`/`success`. A completed non-success fails at once; `queued`/`in_progress`/`not_found`, and `api_error` (a failed `gh api` read, caught with `if ! result=$(…)` so one GitHub 5xx doesn't end the wait through `set -e`), wait until `CI_WAIT_SECONDS` (1800, set in the step `env` and required by the script with `:?`), because a Release run starts while the merge's CI is still running (ADR 0010's Q1). The job's `timeout-minutes` must stay above that wait, or it times out without naming the pending check; a test checks this. The names are read from the ruleset, never copied into the workflow. PR CI runs on `refs/pull/N/merge`, so `ci.yaml` also runs on `push: main` to put checks on the merge commit. `tools/docs-check/test/verify-required-checks.test.ts` runs the script with a fake `gh` (a node script on `PATH` that answers `compare` from `FAKE_COMPARE_STATUS` and returns the n-th round of `FAKE_CHECK_RUNS` on the n-th call per check name, counted in files under `FAKE_STATE_DIR`) and the real `jq`, with `CI_POLL_SECONDS=0`. In shell, brace a variable followed by full-width text (`${result}）`): bash can read the multibyte character's bytes as part of the name.

A drop from a deploy that changes the API code is untested, and the no-API-deploy-during-an-event rule stays. Open tabs keep the old web bundle until a reload. To force a drop, use `page.routeWebSocket` and close the page side; Playwright's `setOffline` and DevTools' Offline leave open WebSockets alone.
- **E2E** (`e2e/`, `playwright.config.ts`, ADR 0003): one Playwright run (`full-game.spec.ts`) of login → editor → room → two players → three questions (①②, ③ on question 1) → final ranking, plus `csp.spec.ts`, which proves the CSP collector catches an inline script, `player-reconnect.spec.ts` (reload, X1 second tab, failed `resume`, server-side drop, name collision, malformed room ID) and `a11y.spec.ts` (axe). CI runs it as the `e2e` job, a required check like `ci`.
  - It runs against `vite build` + `vite preview`, not `vite dev`, because `_headers` (the CSP) applies only there. `apps/web`'s `e2e:serve` wipes `.wrangler/e2e`, runs `CLOUDFLARE_ENV=e2e vite build --mode e2e`, applies migrations with `db:migrate:e2e` and starts `vite preview --mode e2e --port 4173`. `CLOUDFLARE_ENV` goes only on the build: preview reads the flattened `dist/*/wrangler.json`, and `CLOUDFLARE_ENV` there warns about a missing env. `--mode e2e` switches `persistState` to `.wrangler/e2e`, so E2E never touches the `vite dev` data. A different `database_name` doesn't separate local D1 files; the folder does.
  - `env.e2e` in both `wrangler.jsonc` files: the API's `main` is `test/e2e-entry.ts` (named `zubakui-api-e2e`, which the web `env.e2e` binds to). `durable_objects`, `d1_databases`, `secrets` and `services` aren't inherited by an env, so they are repeated there. With an env defined, a plain `wrangler deploy` warns; production deploys pass `--env=""`.
  - `e2e-entry.ts` imports the production `app` and adds only `POST /api/e2e/login` (`test/e2e-login-path.ts`), which makes a fresh host (user, account, allowlist row) per call and returns `testUtils`' `getCookies`, which `context.addCookies` takes as is. The session goes through the real `session.create.before`.
  - `apps/api/vitest.bundle.config.ts` (project `api-bundle`, node, `test/bundle/`) runs `wrangler deploy --dry-run` for both envs and checks that the path is absent from the production bundle and present in the e2e one, so the check can't pass by a typo. The Workers project excludes `test/bundle/`, and `tsconfig.node.json` type-checks it.
  - `apps/api/.dev.vars.e2e` is committed with test values (`.gitignore` re-includes it). With `CLOUDFLARE_ENV=e2e`, wrangler reads `.dev.vars.e2e` before `.dev.vars` and the Vite plugin copies the result into `dist/zubakui_api/.dev.vars`; without it, a developer's real `.dev.vars` would be copied into the E2E build.
  - `vite build --mode e2e` rewrites `apps/web/.wrangler/deploy/config.json` to the E2E build, so always run `vite build` right before a `wrangler deploy` of the web Worker.
  - `a11y.spec.ts` (#116) runs one game through the join form, the host lobby, answering with the host's accepting stage, and the host's ①, and expects `a11yViolations(page)` (`e2e/helpers/axe.ts`: `@axe-core/playwright`, `wcag2a`/`wcag2aa`, violations cut to `{ id, help, targets }`) to be `[]` on each; a second test proves it catches an unnamed button. `color-contrast` is disabled until #126, and #135 turns it back on. axe goes in through `page.evaluate`, which the CSP doesn't block (no `bypassCSP`), but the spec still doesn't collect CSP violations, so `csp.spec`'s context stays separate. The host context from `beforeAll` stays open until `afterAll`, because `/api/e2e/login` makes a new host on every call, and a new one doesn't own the room (4404). The root tsconfig has no DOM types, so a browser-side expression in a spec is passed to `page.evaluate` as a string.

## Writing docs and ADRs

- Docs are written in plain, jargon-light Japanese. Match the existing tone, for example "確かめる" rather than "検証する".
- ADRs use the MADR format at `docs/adr/NNNN-<slug>.md`. The title is the decision itself, and the sections are Status / Context / Decision Drivers / Considered Options / Decision Outcome / Consequences. They are usually authored with the `tech-adr:adr-writer` skill.
- Decision drivers are numbered `DD1`, `DD2`, and so on. ADR 0001 predates this and uses `D1`. Option IDs must not reuse requirement prefixes (`F`/`P`/`S`/`A`/`SC`/`M`/`C`/`O`).
- When a decision changes a requirement, update `docs/requirements/zubatto-quiz.md` in the same change. Past commits show this pattern.
- Check service limits, pricing and API behavior against current docs (context7 MCP first) and state the date checked. The ADRs depend heavily on free-tier numbers.
