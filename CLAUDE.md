# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

ズバッとクイズ (ズバクイ) is a real-time multiple-choice quiz app where players score on both correctness and answer speed. The repo is **early in implementation**: it holds tooling, CI and design documents. The pnpm workspace (`apps/*`, `packages/*`, `tools/*`) is set up. The packages so far are `packages/protocol` (the WebSocket message spec and the HTTP request and response shapes), `packages/scoring` (score and ranking calculation), `tools/docs-check` (tests that keep README and `docs/runbooks/` in step with the repo), `tools/loadtest` (the O2 rehearsal bots: rooms × bots play a whole game and P1, P3 and P4 come out as a Markdown table), `apps/api` (the API Worker: Hono with `GET /api/health`, the question-set HTTP API under `/api/question-sets`, `POST /api/rooms`, the room DO with its SQLite schema, an `initialize` RPC, the WebSocket entries `/api/rooms/:roomId/ws/host` and `/ws/play`, the `join` and `resume` handlers with the unverified-connection timeout and X1 replacement, the host progression commands with the answer deadline, `wrangler.jsonc` and the drizzle D1 schema with its migrations) and `apps/web` (the SPA skeleton: TanStack Router routes, Tailwind tokens, the CSP, the Worker that forwards `/api/*`, and `src/realtime`: the room WebSocket client with auto-reconnect and `resume`, the zustand room store and an in-memory fake WS server for tests; `/r/$roomId` with the player join form, waiting room, connection notices, and the question and answer screen; `/login` and `/admin` with the host's GitHub login, the question-set list and the question-set editor; `/rooms/$roomId/host` with room creation from the list, the host's lobby and the progression screen), and `e2e/` (one Playwright run through the whole game against a production-like build, with a test-only login entry in `apps/api/test/e2e-entry.ts`). Before you design or implement anything, read the documents below. They are the source of truth:

- `docs/requirements/zubatto-quiz.md` is the requirements spec. Requirement IDs are `F*` (functional), `P*` (performance), `S*` (security), `A*` (availability), `SC*` (scalability), `M*` (maintainability), `C*` (cost) and `O*` (operations). ADRs and commits cite these IDs.
- `docs/adr/0001`–`0005` record the accepted architecture decisions. Each ADR's "対応事項" list under Consequences is effectively the implementation checklist.
- `plan.md` holds the original rough idea, including the frontend stack: React + TanStack Start as an SPA with `ssr: false`, TanStack Query, and zustand if needed. Where it conflicts with the requirements or ADRs, those win. TanStack Start was dropped for TanStack Router alone, because its SPA shell needs inline scripts that break `script-src 'self'` (ADR 0006). `memo.md` is a gitignored scratch file.

## Planned architecture (from the ADRs)

The first release is all TypeScript on Cloudflare's free plan. After the first event, the backend will be rewritten in Go on Cloud Run with Terraform (ADR 0001). Keep backend platform specifics out of anything the frontend depends on. In particular, the **WebSocket JSON message spec must be platform-independent and shared between frontend and backend**, so the rewrite doesn't touch the frontend.

- **Runtime**: a Hono Worker plus **one Durable Object per room**. The DO uses the WebSocket Hibernation API and DO SQLite, and it is the single source of truth for room state, scores and answers. There is no polling or SSE.
- **Worker layout** (ADR 0006): two Workers. `apps/web` serves the SPA as static assets and forwards `/api/*` to `apps/api` (Hono + DO + Better Auth) over a Service binding, so the browser sees one origin. No CORS and no `crossSubDomainCookies`. Every API and WebSocket path lives under `/api/`. `apps/api` sets `workers_dev: false` and `preview_urls: false`. Don't deploy `apps/api` during an event, because that drops the room WebSockets.
- **Question sets** (ADR 0002) are stored in D1 and scoped by `owner_id`. Every D1 access layer takes `owner_id` as a required argument. Room creation reads the whole set from D1 once and writes it into the room DO's SQLite in a single transaction. During play, the room never reads D1 again. Correct answers never leave the DO before the deadline (S2).
  - The HTTP API in `apps/api/src/routes/question-sets.ts` only maps the repository's `undefined`/`false` to 404, so another host's set looks the same as a missing one. Errors are `{ error: code }` from protocol's `httpErrorSchema`. `routes/common.ts` holds the shared `jsonBody` (400 on a schema mismatch) and `notFound`.
  - `getQuestionSet` also returns each question's D1 `id`, which the room keeps as its `questionId`. `GET /api/question-sets/:id` strips it to match `QuestionSetDetail`.
  - `POST /api/rooms` (`routes/rooms.ts`) reads the set with `getQuestionSet`, creates the DO with `newUniqueId()` (S3; never `idFromName`) and calls the `initialize` RPC. That RPC refuses a second call and writes the room row and the questions in one `transactionSync`. The response carries `roomId` (`id.toString()`, 64 hex chars) and `joinUrl`, which is `BETTER_AUTH_URL` + `/r/:roomId`.
  - Cookie-authenticated routes that change state use `.use(csrf(), requireHost)`, with `csrf()` first so it rejects before reading the session. `csrf()` treats a request with no `Content-Type` (a body-less `DELETE`) as `text/plain`, so tests must send `Origin` and `Sec-Fetch-Site: same-origin` the way a browser does.
- **Host auth** (ADR 0003): Better Auth with GitHub login. `owner_id` is Better Auth's `user.id`.
  - The allowlist of GitHub user IDs is checked on sign-up in `user.validateUserInfo`, before any row is written. D1 has no transactions, so a rejection in `account.create.before` would leave a `user` row behind. It is checked again on every session creation in `databaseHooks.session.create.before`.
  - `apps/api/src/auth`: `createAuthOptions(env)` is shared by the production `createAuth` and the test-only `test/auth/create-test-auth.ts`, which only adds `testUtils`. oxlint blocks importing `testUtils` and `better-auth/test` outside test code. `testUtils.saveUser` goes through `validateUserInfo` and is rejected, so tests insert `user` and `account` rows with drizzle.
  - `BETTER_AUTH_URL` (the web Worker's URL) and the secrets are listed under `secrets.required` in `apps/api/wrangler.jsonc`, so `wrangler types` doesn't depend on `.dev.vars` and `wrangler deploy` fails if one is unset. The URL isn't secret, but a `vars` entry is reset to its file value on every deploy, so a forgotten override would silently send GitHub's callback to localhost. Locally the values go in `apps/api/.dev.vars`; `vitest.config.ts` passes test values.
  - The host WebSocket entry checks `Origin`, resolves `ownerId` from the cookie session and passes it to the DO.
  - `routes/ws.ts` checks, in order, `Origin` against `new URL(c.req.url).origin` (403, also when missing, before any cookie is read), `Upgrade` (426) and the room ID (64 lowercase hex chars and `idFromString`, else `refuseConnection('room_not_found')`, 4404). The host entry then runs `requireHost`.
  - The Worker never forwards the browser's request to the DO. `roomRequest` in `room/connections.ts` builds a new one with only `Upgrade` and, for the host, the internal owner header, so cookies and a forged owner header never reach the DO.
  - `index.ts` registers `wsRoutes` before `roomRoutes`, because `roomRoutes`' `csrf()` and `requireHost` cover all of `/api/rooms/*`. A test fails with 401 on the player entry if the order flips.
  - The DO's `fetch` is synchronous. It closes with 4404 `room_not_found` (`refuseConnection`) for a room that was never initialized and for a host who isn't the owner, checked before `ended_at`, so another host's room looks missing, the same as the HTTP API's 404 (S1). Never refuse a browser's WebSocket with an HTTP status: the browser can't read it and sees 1006, so the client reconnects forever. Only a request `readRoomEntry` can't read (never from a browser) gets HTTP 404.
  - The DO records the attachment `{ role: "host", ownerId }` only when that ID owns the room. An ended room refuses the host with 4410 `room_ended` (`refuseConnection`). An accepted host gets `hostReady`, then `participants`, then the resend, all sent inside the synchronous `fetch` before the 101 is returned; they still arrive after the client opens.
  - Progression commands are accepted only from host-role connections. `webSocketMessage` checks `isHostCommand` and the attachment role, and answers `not_host` to a player socket, before `handleHostCommand` (`room/handlers/host-commands.ts`) runs.
  - The progression order is the pure `transition` in protocol's `room-flow.ts`, tested as a table. The host screen's `canSend(room, command)` wraps it, so a button is enabled exactly when the DO would accept the command. A command whose phase or `questionIndex` doesn't match gets `invalid_state`. After the deadline the only path is ① `revealed` → ② `fastest` → (③ `standings`) → the next `showQuestion`, or `showFinalRanking` after the last question. `canShowStandings` rejects ③ in the last two questions, so a room of two questions or fewer never shows it. `retryQuestion` works only before the deadline (`question`/`accepting`): it deletes that question's `answers`, goes back to `question` and re-sends `questionShown`. `endRoom` works from any phase and closes every socket, unverified ones included, with 4410 `room_ended`.
  - `applyHostCommand` reads state, calls `transition`, writes `room` (and the retry's `DELETE`) in one `transactionSync`, then broadcasts. It never reads `questions.correct_index` itself (S2) and never touches D1 or `fetch` (P1). `questionShown` has no choices; `answeringStarted` adds them. For ①②③ and the final ranking it calls `sendResults` after the commit.
  - Deadline scoring (`room/handlers/close-question.ts`): on `closeAnswering`, `scoreQuestion` runs inside the same `transactionSync` that moves the phase to `revealed`. It reads `correct_index`, scores each answer with `scoreAnswer`, writes `question_scores` (answered rows only; no row means 0) and sets `questions.closed_at`, skipping a question that already has one. `scoreQuestion` and `results.ts` are the only code outside `initialize` that touches `correct_index`.
  - Results (`room/results.ts`) are never stored. `readQuestionOutcome` rebuilds a closed question's outcome from `question_scores` and `answers` with a fixed number of queries (P4), and the pure `revealedFor`/`myResultsFor`/`fastestFor`/`standingsFor`/`finalRankingFor` turn it into protocol messages through scoring's functions. ① sends `revealed` to hosts and each player only their own `myResult`; ②③ and `finalRanking` go to everyone. The resend calls the same functions.
  - Resend (`room/resend.ts`): after `joined`/`resumed`/`hostReady`, `resendCurrentPhase` sends only to that socket the current question's flow from the start, in `QUESTION_FLOW` order up to the current phase: `questionShown`, `answeringStarted` (`remainingMs` = `max(0, deadline_at - now)`, 0 after the deadline), then ① (`revealed` to a host, the player's own `myResult`), ②, ③. The client store needs `questionShown` first, because it drops messages for another `questionId`. While accepting, a host also gets `answerProgress` and a player who already answered gets `answerAccepted`. `final` sends only `finalRanking`; `lobby` sends nothing. It reaches `results.ts` only after the deadline, so a resend never carries `correctIndex` early (S2). `questionShownOf`/`answeringStartedOf`/`answerProgressOf` there are also what the broadcasts in `host-commands.ts` and `answer.ts` use.
  - The previous ranking (for `rankUp` and the biggest climber) holds only participants whose `joined_at` is at or before the previous question's `closed_at`, so a late joiner never counts as climbing. Question 1 has none.
  - Rank-related info (`position: hidden`, `fastest.ranksHidden`) is hidden exactly when `canShowStandings` is false, so a room of two questions or fewer hides it on every question.
  - `room.deadline_at` (room schema v2) holds `now + limit_ms` only while accepting and the room isn't ended. The alarm's `closeAnsweringIfDue` sends a `closeAnswering` through the same `applyHostCommand`, so a re-run alarm finds no deadline and does nothing. An alarm can be up to a minute late, so `handleHostCommand` calls `closeAnsweringIfDue` before applying any command; otherwise a `retryQuestion` past the deadline would delete final answers. `handleAnswer` calls it before its accepting check for the same reason, so an answer past the deadline gets `not_accepting` even before the alarm fires.
- **Players** (ADR 0004) use a separate entry that never reads cookies.
  - The client generates a 32-byte secret, stores it in localStorage per room, and sends `join { name, token }` or `resume { token }` as the first WS message. The secret is never put in a URL or a log.
  - The DO stores only a SHA-256 hash and compares hashes with `timingSafeEqual`.
  - A `null` attachment means the connection is unverified. Unverified connections may send only `join` or `resume`; anything else gets `error { code: 'not_verified' }`.
  - `webSocketMessage` in `room-do.ts` decodes and dispatches on the attachment. Each message type's logic goes in `room/handlers/` (`join.ts`, `resume.ts`, `host-commands.ts`, `answer.ts` and `close-question.ts` so far). Send with `send`/`broadcast`/`sendToHosts` from `room/send.ts`: `send` skips sockets that aren't `OPEN`, `broadcast` reaches only host and player sockets, never unverified ones, and `sendToHosts` reaches only host sockets.
  - `handleJoin` awaits `hashToken` first, then re-checks that the socket is still `OPEN` and its attachment still `null`. `crypto.subtle.digest` isn't a storage call, so the `await` lets the alarm or a new connection close the socket on timeout, and a second `join` on the same socket can pass too. Name collisions compare `normalizeName` (NFKC, then strip every `\p{Default_Ignorable_Code_Point}`, ZWJ and variation selectors included, then trim; case-sensitive). protocol's name check rejects only Cc and Cf, so invisible characters outside Cf would otherwise let a player pose as someone else. A name that normalizes to `''` gets `invalid_message`. A rejected `join` closes with `room_ended`/`room_full`/`name_taken`; a bad token never reaches the handler, because `decodeClientMessage` rejects it as `invalid_message`.
  - `handleResume` (`room/handlers/resume.ts`) follows the same `await`-then-recheck pattern. `resume` carries no `participantId`, so it reads every `participants` row (50 at most) and compares hashes with `timingSafeEqual`, never `WHERE token_hash = ?`. An ended room closes with `room_ended`; a wrong token or one past `RESUME_WINDOW_MS` (6 h from `joined_at`) closes with `resume_failed`. `resumed.score` is `sum(question_scores.points)`.
  - X1: after a `resume` passes, `closeReplacedConnections` (`room/replace-connection.ts`) closes every other socket whose attachment has the same `participantId` with 4301 `replaced`, before `resumed` is sent. `join` doesn't call it, because its `participantId` is new. Calling `close()` again on a `CLOSING` socket doesn't throw (checked 2026-10-12).
  - `test/room-socket.ts` has `joinPlayer`, `resumePlayer` and `connectHost` (reads `hostReady` and `participants` first, so a lobby test sees only later broadcasts). `resume` also sends `participants` to that socket, after `resumed`. `evictDurableObject(stub, { webSockets: 'close' })` drops the old client with 1006; a plain evict keeps it, so the next `resume` replaces it with 4301.
  - Unverified sockets are accepted with the tag `acceptedAt:<ms>` (`pending-timeout.ts`) and closed with 4408 `join_timeout` 10 s later, both by the DO `alarm()` and by `acceptConnection` before it counts. `scheduleAlarm` (`room/alarm.ts`) recomputes the next alarm from state, as the earlier of the oldest pending deadline and `room.deadline_at`, never from `getAlarm()`. It runs on every player connection, on `startAnswering` and at the end of `alarm()`.
  - `participantId` always comes from the attachment, never from the message body.
  - A new connection for the same participant closes the old one, and the old tab does not auto-reconnect.
- **Concurrency invariants**:
  - Count `getWebSockets()` against the connection cap before `acceptWebSocket`, with no `await` in between. `countOpenConnections` counts only `OPEN` sockets, because a socket the DO closed stays in the list as `CLOSING`.
  - The cap is per entry: 100 for the player entry (unverified sockets included) and a separate 5 for host sockets, told apart by the attachment role. A flood on the player entry must never lock the host out (#69).
  - Over the cap, `acceptConnection` returns no `accepted` socket and `refuseConnection` calls `server.accept()` (not hibernatable, not in `getWebSockets()`) and closes with 4503 `connection_limit`, so the client can tell it apart from other failures.
  - Run the `join` checks (name collision after NFKC normalization and trim, the 50-player cap `MAX_PARTICIPANTS` from protocol, which the host lobby also shows) and the insert as synchronous SQL with no `await`.
  - Enforce one answer per question with `UNIQUE(question_id, participant_id)` and an accepting-answers check in one transaction.
  - `handleAnswer` (`room/handlers/answer.ts`) accepts `answer` only from player-role sockets (a host socket gets `invalid_state`). In one `transactionSync` it reads the accepting question (`not_accepting` when the phase isn't `accepting`, the room has ended or `questionId` isn't the current question), checks `choiceIndex` against that question's choice count (`invalid_choice`), then inserts with `ON CONFLICT (question_id, participant_id) DO NOTHING` and maps `rowsWritten`/`changes()` = 0 to `already_answered`. Never use `INSERT OR IGNORE`: it also swallows CHECK violations, which would read as `already_answered`.
  - `answers.elapsed_ms` stores the `normalizeElapsedMs` value: the client's value is trusted (P2), one above `limitMs` is clamped to it rather than rejected, and a negative one fails decode as `invalid_message`. `answerAccepted` echoes the stored value. `answerProgress` goes only to host sockets, never to players.
- **Message spec** (`packages/protocol`): zod schemas for the WebSocket messages, close codes, the question-set shape and the HTTP request and response shapes (`src/http/`). The frontend calls the HTTP API with these schemas, not Hono RPC, so it doesn't depend on Hono.
  - The room DO must decode input with `decodeClientMessage` and send through `encodeServerMessage`. Both strip unknown fields, so a stray `participantId`, `correctIndex` or `rank` never crosses the wire.
  - `schema/ws.schema.json` is generated, and it is the source of truth for the Go rewrite. After changing a schema, run `pnpm --filter @zubatto-quiz/protocol run schema`. A test fails when the file is stale.
  - `schema/openapi.json` (OpenAPI 3.1, `src/openapi.ts`) is the same for the HTTP API: `/api/question-sets` and `POST /api/rooms`, written by the same `schema` script and checked the same way. Request bodies use `toDef(schema, 'input')`, responses `'output'`; OpenAPI 3.1 takes zod's JSON Schema 2020-12 as is. When a route's status codes change, update its `responses` and the table in `openapi.test.ts`. The `csrf()` 403 and the malformed-JSON 400 are `text/plain`. Conditions JSON Schema can't express (`.refine()`, `.trim()`) go in a `.meta({ description })` or `info.description`. The test runs `@readme/openapi-parser`'s `validate` on the committed file, read again for each call, because it resolves `$ref`s in place. No `@hono/zod-openapi` and no Swagger UI in the Worker; view it locally as one HTML file with `pnpm dlx --package=@redocly/cli@<ver> redocly build-docs packages/protocol/schema/openapi.json -o .playwright-mcp/openapi.html` from the repo root (CLI v2's `preview` is for Redocly projects and can't open a single file; checked 2.57.0, 2026-10-18).
  - `tsconfig.json` (with node types) is for the editor and the tests. `tsconfig.lib.json` checks non-test `src/` with no ambient types, so a Workers, DOM or node dependency fails `pnpm run tsc`.
- **XSS hardening** replaces HttpOnly here:
  - CSP `script-src 'self'`, set in `apps/web/public/_headers`. Keep `apps/web/index.html` free of inline scripts, styles and event handlers; a test checks both files. `_headers` applies to `vite build`/`vite preview`/deploy but not `vite dev`, and never to Worker responses (`/api/*`).
  - Markdown (F5) renders no raw HTML.
  - Never use `innerHTML`-style APIs for user-provided names.
- **Infra** (ADR 0005): `wrangler.jsonc` is the only IaC. It holds the Worker, the DO `new_sqlite_classes` migration and the D1 binding.
  - Secrets go in with `wrangler secret put`.
  - Anything that can't be expressed in config goes in the runbooks under `docs/runbooks/` (linked from README): the GitHub OAuth Apps for local and prod, the secrets, the allowlist, usage checks and the stop procedure (delete the Worker), and the `main` ruleset. When a change affects one of them (a secret, a table, a command, the CI job name), update the runbook in the same change.
  - `docs/runbooks/main-ruleset.json` is the `main` ruleset as `gh api -X POST .../rulesets --input` takes it (no `id`, `_links` or other server fields). `tools/docs-check` (vitest project `docs`) checks that each required check matches a job's check name in `ci.yaml` (`jobs.<id>.name`, else the job ID; the test hardcodes no name), and that every relative link and `#anchor` in README, CONTRIBUTING and the runbooks stays inside the repo and resolves (GitHub's heading slugs).
  - `wrangler deploy` refuses a first deploy of a Worker with `secrets.required` unset. `wrangler secret put` on a missing Worker creates an empty one, so production runs `secret put` before the first deploy and the deploy workflow never holds app secrets (checked in wrangler 4.149.0 source, 2026-10-17). Deleting a Worker deletes its secrets; D1 stays.
  - Production deploys run only from `.github/workflows/deploy.yaml`, started by hand (`workflow_dispatch`, `target: web | all`, default `web`). `all` is `migrate` → `deploy-api` → `deploy-web`, chained by `needs`. `deploy-web` has `if: ${{ !failure() && !cancelled() }}`: a job-level `if` with no status function counts as `success() && …`, so without it `web` would skip `deploy-web` along with the skipped API jobs. Every job has `environment: production`, the only place the Cloudflare token and account ID live, and the Environment allows only `main` (`docs/runbooks/deploy.md`). `concurrency` keeps GitHub's default single pending run (a newer dispatch cancels the pending one, and the runbook says to re-run a cancelled `all`); don't add `queue: max`, whose order isn't guaranteed, so an older commit could deploy last. Jobs call root `db:migrate:remote`/`deploy:api`/`deploy:web`; the API ones pass `--env=""`, and web's `deploy` is `vite build && wrangler deploy`.
  - `tools/docs-check/test/deploy-workflow.test.ts` reads both workflows with `yaml` and simulates which jobs run per target and failing job. Its `evaluateIf` knows only the expressions the workflow uses and throws on anything else, so extend it when you change a condition.
  - `apps/api/.dev.vars.example` lists the `secrets.required` names with empty values (except `BETTER_AUTH_URL`); `.gitignore` re-includes it. `tools/docs-check` fails if the names drift from `wrangler.jsonc` or a secret gets a value.
  - `host_allowlist.github_user_id` is TEXT: write `'12345'`, never `12345`, or it won't match `account.account_id`.
  - No Terraform until the Go migration.
- **D1 schema** (`apps/api/src/db`): drizzle tables for Better Auth, `question_sets`, `questions` and `host_allowlist`. Use `createDb(env.DB)`.
  - `schema/auth.ts` is the output of the Better Auth CLI (`auth`, formerly `@better-auth/cli`). The CLI needs a config file. Regenerate it when you upgrade Better Auth or add a plugin, and keep the hand-added `(provider_id, account_id)` unique on `account`: Better Auth refuses to look up an account that has duplicate rows.
  - `questions.choices` is a JSON array column. The DB CHECK constraints copy the rules in protocol's `questionSchema` (2–4 choices, all of them strings, correct index in range, F9 limits) and take their numbers from protocol's constants.
  - `migrations/` is generated. Run `pnpm --filter @zubatto-quiz/api run db:generate --name <name>` and don't edit the SQL by hand; oxfmt skips `migrations/meta`. Once a migration is deployed, only add new ones, and keep them additive so the old code still runs (ADR 0005).
  - `pnpm --filter @zubatto-quiz/api run db:migrate:local` applies them to the local D1 that `vite dev` uses (`apps/web/.wrangler/state`).
  - In tests, `test/apply-migrations.ts` applies `migrations/` before each test file. vitest-plugin does not reset D1 between tests, so clear tables in `beforeEach`. drizzle wraps D1 errors, so assert on `cause.message`.
- **Room DO SQLite** (`apps/api/src/room`): no drizzle. Use `ctx.storage.sql` directly, so the `join` checks and insert stay synchronous.
  - `schema.ts` holds `ROOM_MIGRATIONS`, one SQL string per version. The constructor runs `migrate` inside `blockConcurrencyWhile`. Each version and its `schema_migrations` row are applied in one `transactionSync`. Never edit a deployed version; append a new one.
  - DO SQLite doesn't support `PRAGMA user_version` (checked 2026-10-12), so the version lives in `schema_migrations`.
  - Tables are `STRICT`. `participants.join_order` is the rowid alias and is the scoring `joinOrder`. ## Writing docs and ADRs

- Docs are written in plain, jargon-light Japanese. Match the existing tone, for example "確かめる" rather than "検証する".
- ADRs use the MADR format at `docs/adr/NNNN-<slug>.md`. The title is the decision itself, and the sections are Status / Context / Decision Drivers / Considered Options / Decision Outcome / Consequences. They are usually authored with the `tech-adr:adr-writer` skill.
- Decision drivers are numbered `DD1`, `DD2`, and so on. ADR 0001 predates this and uses `D1`. Option IDs must not reuse requirement prefixes (`F`/`P`/`S`/`A`/`SC`/`M`/`C`/`O`).
- When a decision changes a requirement, update `docs/requirements/zubatto-quiz.md` in the same change. Past commits show this pattern.
- Check service limits, pricing and API behavior against current docs (context7 MCP first) and state the date checked. The ADRs depend heavily on free-tier numbers.
